# Релизный чеклист

Один путь от `master` до стабильного выпуска у всех. Как устроена сборка выпуска, подпись и раскатка —
[docs/architecture/release.md](../architecture/release.md); что делать, когда с выпуском что-то не так, —
[support.md](support.md). Пункт не выполнен — выпуска нет: «потом проверим» здесь не бывает.

## 1. Перед тегом

- [ ] `master` на коммите выпуска, проверка CI на нем зеленая целиком: «Сборка и тесты» на трех ОС, «Стиль и формат»,
      «Другие процессоры» (Linux ARM, Mac с Intel), «Секреты в репозитории», Android и «Android (эмулятор)». В сводке заданий — ни одного пропуска вне
      `desktop/tests/allowed-skips.json`.
- [ ] Долгий прогон (`soak.yml`) — ночные запуски на `master` зеленые. На коммите тега его гоняет сам выпуск (задание
      «Долгий прогон» в `release.yml`, 30 минут на режим): режим прокси на трех ОС, VPN на Linux и Windows, утечек нет,
      ресурсы не растут. Красный — выпуск не публикуется.
- [ ] `publish.yml` на коммите выпуска зеленый на трех ОС: пакеты ставятся и удаляются, смоук выпуска проходит.
- [ ] Открытых пунктов о сбоях и утечках в ROADMAP (README, этапы 3, 4 и 11) нет — или у каждого записано, почему он не
      держит выпуск.
- [ ] Проверка пользователем на своих машинах по [windows-check.md](../testing/windows-check.md) и
      [android-check.md](../testing/android-check.md) для того, что в CI не проверить (настоящая сеть, TUN без узкого
      маршрута, телефон): итоги — пунктами в ROADMAP. Для беты достаточно Windows или Linux; для стабильного — все ОС
      выпуска.
- [ ] Лицензии: `shared/licenses/components.json` и `shared/licenses/android.json` покрывают все пакеты — иначе выпуск и
      APK не собираются сами; новые ядра и шрифты — со строкой и текстом лицензии.
- [ ] Секреты: `gitleaks` по истории с прошлого тега чистый; в журналах и отчете проверки — `SecretMasker`.
- [ ] Ключ подписи обновлений: секрет `UPDATE_SIGNING_KEY` есть, его открытый ключ — в `shared/update/keys`. Ключ в
      репозитории уже есть, поэтому без секрета выпуск не собирается: неподписанный манифест программа не примет.
- [ ] Сайт Private Gateway Web принимает ленту обновлений (`import-release.sh`: команды `asset`, `update-sig`,
      `update`) и отдает ее программе (`GET /api/app/updates`) — выпуск 0.3.0 и новее только после развертывания сайта;
      секреты `WEBSITE_*` в репозитории есть.
- [ ] Версия: одна на все платформы — `<Version>` в `Directory.Build.props` (десктоп, Android `versionName`, iOS);
      `scripts/release.sh` ставит в него номер выпуска сам, `versionCode` Android считается из номера.
- [ ] История: в `CHANGELOG.md` пункты из `## [Не выпущено]` перенесены в новую секцию `## [X.Y.Z]` — коротко, для
      людей, по шаблону в начале файла, без «@слов»; из нее собираются «Что нового» на странице выпуска и до трех строк
      карточки обновления в окне. Секции нет — выпуска нет. Текст страницы заранее: `scripts/release-notes.sh X.Y.Z`.

## 2. Бета

- [ ] Бета (номер с суффиксом) — тегом вручную: `git tag -a vX.Y.Z-beta.N -m "Private Gateway X.Y.Z-beta.N"` и
      `git push origin vX.Y.Z-beta.N` на проверенном коммите `master`; секция в `CHANGELOG.md` — `## [X.Y.Z-beta.N]`.
      `scripts/release.sh` выпускает только X.Y.Z, как в SmartBase. `release.yml` сам сверяет версию и секцию, SHA,
      принадлежность `master`, зеленую CI этого SHA и гоняет долгий прогон до сборки; при отказе — исправить причину и
      повторить запуск тега («Re-run»).
- [ ] `release.yml` зеленый, выпуск на GitHub помечен предварительным, в нем файлы трех ОС и APK, `SHA256SUMS`,
      `update.json` (с `android-apk`) и `update.json.sig`.
- [ ] Загрузка сверяется: `sha256sum -c SHA256SUMS` в папке скачанных файлов.
- [ ] Установка с нуля на чистой машине каждой ОС — файлами выпуска на GitHub: бета на сайт не попадает. Обновление
      через «О программе» на бете не проверить — лента сайта пока только стабильная; его, «Откатить на …» и
      «Скачать и установить» на Android проверяют на стабильном выпуске (раздел 3): защита после каждого шага
      держится, блок при обрыве не выпускает трафик, пока служба меняется.
- [ ] Бета живет не меньше недели без сообщений о сбоях из раздела «Серьезность» [support.md](support.md) уровней 1 и 2.

## 3. Стабильный выпуск

- [ ] Выпуск — одним из двух путей, они делают одно и то же:
      - **компьютер:** `scripts/release.sh X.Y.Z` в основной папке на `master` (сначала `--dry-run`): проверки, план,
        «Выпустить? [y/N]», затем коммит `release: vX.Y.Z` с датой секции, аннотированный тег и отправка;
      - **кнопка на GitHub** (телефон, браузер или агент через API): Actions → «Выпустить версию» → Run workflow →
        Use workflow from — `master` → «Версия X.Y.Z, например 0.2.2» → Run workflow (сначала с флажком «Только
        проверки, ничего не менять»). Тот же `release.sh` с `--yes`; затем кнопка сама запускает «Проверку» на `master`
        и «Выпуск на GitHub» на теге. Шаги по экранам — [release.md](../architecture/release.md), «Кнопка «Выпустить
        версию»».

      Дальше — GitHub (около двух часов): «Выпуск на GitHub», затем «Выпуск на сайт»: установщики, rpm, подпись и
      манифест — с этой минуты программы участников видят обновление.

- [ ] Выпуск, которому нужен новый API сайта Private Gateway Web, — только после развертывания сайта: 0.2.1 без нового
      входа на сайте получил бы 422 на первом шаге, и войти не смог бы никто.

### Если отправка тега оборвалась

`release.sh` отправляет на GitHub два раза подряд: сначала `master`, потом тег. Второе соединение GitHub иногда обрывает
по пути — в выводе `Connection closed by 140.82.x.x port 22` и `fatal: Could not read from remote repository` (так было
с 0.2.0). Это сбой связи, а не прав и не выпуска: `master` с коммитом `release: vX.Y.Z` уже на GitHub, тег создан у вас.
Скрипт сам повторяет отправку тега до четырех раз (через 2, 4, 8 и 16 с); если не помогло — останавливается с
подсказкой. Тогда в Git Bash, в основной папке на `master` (пример для 0.2.1 — подставьте свою версию):

1. Тег стоит на коммите выпуска — команда печатает тот же короткий хеш, что у `release: v0.2.1` в `git log -1 --oneline`:

   ```bash
   git rev-parse --short "v0.2.1^{}"
   ```

2. Отправить тег:

   ```bash
   git push origin v0.2.1
   ```

   Ответ `* [new tag] v0.2.1 -> v0.2.1` — выпуск запущен (Actions → «Выпуск на GitHub»). Если SSH снова обрывается —
   то же через HTTPS (Git спросит вход в GitHub):

   ```bash
   git push https://github.com/rvburov/private-gateway-client.git v0.2.1
   ```

`release.sh` второй раз не запускать: тег уже есть, и скрипт откажет («тег занят»). Удалять тег тоже не нужно.

У кнопки тег уходит с машины GitHub. Если она остановилась на отправке тега (`master` уже на GitHub, тега нет) —
нажмите кнопку еще раз с той же версией: коммит выпуска уже в `master`, в тот же день (UTC) нового не будет, и тег
встанет на него. Если
остановилась уже после отправки тега («Не удалось запустить …») — кнопку не повторять: Actions → «Проверка» → Run
workflow (`master`), если у коммита выпуска ее нет, затем «Выпуск на GitHub» → Run workflow → Use workflow from →
Tags → `vX.Y.Z` → Run workflow.
- [ ] `release.yml` зеленый; раскатка — 100 % сразу (решение владельца 2026-11-13); на странице выпуска — «Что нового»
      из секции, таблица установки, первый запуск, никаких участников в «Contributors».
- [ ] «Выпуск на сайт» зеленый, последняя строка сводки — `На сайте: update X.Y.Z update.json`. На машине с прошлой
      версией (вход в аккаунт выполнен) «О программе» → «Проверить» показывает X.Y.Z, «Обновить сейчас» ставит ее. Так —
      с выпуска после 0.3.0: 0.2.x ленту сайта не знает, 0.3.0 все ставят вручную со страницы «Скачать клиент».
- [ ] Сообщение уровня 1–2 — стоп-кран: `release-rollout.yml`, тег и доля 0 ([support.md](support.md)). Задание
      «Сайт — новая доля» должно стать зеленым: программы берут ленту с сайта, и пока оно красное, у них прежняя доля.

## 4. После выпуска

- [ ] В ROADMAP — отметка о выпуске с датой. `<Version>` в `Directory.Build.props` остается номером выпуска: следующий
      ставит `release.sh`. Поднять заранее можно только вместе с секцией `## [X.Y.Z]` в `CHANGELOG.md` — без нее
      падают проверки выпуска (`scripts/tests/release-test.sh`, пункты 2а и 6).
- [ ] Сообщения пользователей — по [support.md](support.md); найденное — пунктами ROADMAP.
- [ ] Подписи кода Windows и macOS — пока в разделе ROADMAP «Отложено»: в заметках выпуска сказано, как поставить
      неподписанную программу.
