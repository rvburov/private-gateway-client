# Windows 10: обрыв VPN через раздачу iPhone и обновление подписки

Дата: 2026-11-02. Статус: реализованы исправления клиента, ручная проверка исходного случая Windows/iPhone открыта.
Первичный разбор ниже отделен от последующих изменений кода; причина конкретного обрыва TCP не объявляется доказанной.

исправлением без связи с установленным дефектом.

## Подписка, TCP Vision и XHTTP

Подписка — один адрес обновления и группа серверов. Ее ответ может содержать несколько готовых профилей, например
TCP Vision и XHTTP. Это разные варианты подключения внутри одной подписки, а не две автоматически созданные подписки.
Одна VLESS-ссылка дает один профиль; код не добавляет к ней второй транспорт.

- [ServerSubscription](../../../desktop/src/Client.Core/Servers/ServerSubscription.cs) хранит одну группу и ее адрес.
- [ImportParser](../../../desktop/src/Client.Application/Import/ImportParser.cs) разбирает записи ответа;
  [LinkParser](../../../desktop/src/Client.Application/Import/LinkParser.cs) сохраняет транспорт и имя каждой ссылки.
- [SqliteServerCatalog](../../../desktop/src/Client.Infrastructure/Storage/SqliteServerCatalog.cs) различает
  конечные точки с разными транспортами. Сами TCP Vision и XHTTP поддерживаются
  [XrayConfigBuilder](../../../desktop/src/Client.Network/Xray/XrayConfigBuilder.cs).

В приложенных файлах нет ошибки загрузки подписки, HTTP-кода, предпросмотра импорта или обезличенного ответа
поставщика. Поэтому нельзя утверждать, что конкретная подписка возвращает два профиля, что ссылка недействительна
или что обнаружено дублирование. Ответ поставщика также может зависеть от формата и `User-Agent` клиента — см.
[совместимость импорта](../../architecture/import.md#совместимость-с-private-gateway).

Обновление уже сохраненной подписки по умолчанию разрешено только через VPN (`AppSettings.UpdateOnlyViaVpn`).
[SubscriptionUpdater.Block](../../../desktop/src/Client.Application/Servers/SubscriptionUpdater.cs) запрещает его
без активного VPN, при переподключении и паузе. Разрешенная загрузка идет через
[Gateway.Subscriptions](../../../desktop/src/Client.Service/Gateway.Subscriptions.cs) и парольный вход ядра;
[SubscriptionTransport](../../../desktop/src/Client.Service/Cores/SubscriptionTransport.cs) не повторяет ее напрямую
при обрыве. Возможна цепочка «VPN не подключается → подписка не обновляется», хотя URL остается действительным.

Первоначальный ручной импорт через
[ImportPageViewModel](../../../desktop/src/Client.UI/ViewModels/ImportPageViewModel.cs) использует обычный
[HttpSubscriptionDownloader](../../../desktop/src/Client.Infrastructure/Import/HttpSubscriptionDownloader.cs).
Это другой путь: стандартный прокси .NET может учитывать переменные окружения. При ошибке соединения с чужим прокси
предусмотрен один прямой повтор; он не гарантирует доступ под действующей блокировкой. Загрузчик VPN-only использует
явный SOCKS ядра и порт 2334 из окружения не выбирает. Ошибка обновления не должна удалять прежний список серверов.

### Основания для HS-02 и HS-03

В отчете 1235: подключение в 12:34:55, Xray в 12:34:56, «Защита выключена» в 12:34:57, затем запуск TUN в
12:35:01–02. [Gateway.DisconnectAsync](../../../desktop/src/Client.Service/Gateway.cs) меняет сессию, но не отменяет
`_starting`; `StopCoreAsync` видит только опубликованные ядра. `VpnTunnel.StartAsync` создает ядра, TUN и маршруты
до проверки актуальности сессии в `StartTunnelAsync`. После завершения запуска устаревший туннель удаляется,
а `_tunnel` публикуется только для текущей сессии. Поэтому сетевые изменения могут продолжаться после отключения.
Очистка под общим семафором также задерживает следующие команды. Это не доказательство постоянного deadlock окна.

[Gateway.CheckExitAsync](../../../desktop/src/Client.Service/Gateway.Leaks.cs) обновляет `Protection.CheckedAt` даже
при отсутствии полученного IP, сохраняя прежний `AllTraffic`.
[MainPageViewModel](../../../desktop/src/Client.UI/ViewModels/MainPageViewModel.cs) берет это время для подписи;
[ProtectionViewModel](../../../desktop/src/Client.UI/ViewModels/ProtectionViewModel.cs) берет «IP скрыт» из Connected.
Первоначальный Connected требует ответа через ядро, но последующий обрыв может некоторое время оставаться зеленым.

### Гипотезы для HS-05

- `Gateway.PickAddresses` предпочитает IPv4, `VpnTunnel` закрепляет первый адрес; переподключение использует прежние
  `_addresses`, без перебора остальных. Другой клиент с тем же профилем может выбрать иной IP/семейство.
- `VpnTunnel.OutsideInterface` выбирает первый внешний default route без сортировки метрик. В отчетах ошибочный
  выбор карты не зафиксирован: внешний маршрут ведет через Wi-Fi.
- MTU Wi-Fi 1450 и TUN 65535 дают основание для сравнения 1420/1280, но не доказывают ошибку PMTU. «Авто» сейчас
  оставляет параметр MTU ядру, а не выполняет адаптивный подбор.
- Необходимо сравнить фактические отпечаток TLS и фрагментацию: настройки клиента могут отличаться при той же ссылке.

## Инварианты защиты

Реализация Windows использует [WfpKillSwitch](../../../desktop/src/Client.Platform.Windows/WfpKillSwitch.cs)
и [WfpRules](../../../desktop/src/Client.Platform.Windows/WfpRules.cs); общая схема — в
[карте сети](../../architecture/network.md).

- При включенном блоке и потере туннеля обычный трафик остается закрытым, но минимальные разрешения для VPN-сервера
  должны позволять переподключение. Самостоятельно открывать весь интернет ради загрузки подписки нельзя.
- Выключенный блок при обрыве не означает отсутствие всей фильтрации: пока VPN поднят, `Gateway.Block` сохраняет
  правила «только туннель», а при обрыве снимает их. Поэтому этот переключатель сам по себе не исключает WFP из причин.
- Явное отключение VPN со снятием защиты и строгий режим имеют разные обещания. Строгий режим после отключения
  сохраняет блокировку по выбору пользователя; обычное выключение возвращает прежние настройки ОС, которыми управлял
  клиент, не перезаписывая изменения других программ.
- Нельзя считать восстановление обычного интернета исправлением VPN, а успешный TCP — проверкой TLS, HTTP или утечек.

Предварительная проверка ограничена общим «Таймаутом подключения» (по умолчанию 10 с), включает запуск ядра и
настоящий запрос через выбранный профиль, а не только ICMP/TCP. Адреса пробуются последовательно с минимальным
бюджетом холодного запуска; общий срок не увеличивается, все адреса большого DNS-ответа могут не успеть провериться.
«Нет» из старого замера не является вечным запретом: профиль мог восстановиться.

Граница этой проверки: она выполняется до первого включения из открытой сети, без уже опубликованного ядра или
действующего блока. При работающем VPN и сохраненном Kill Switch остается защищенная ограниченная попытка и
уведомление; сохранение прежнего VPN при выборе любого недоступного другого профиля не обещается. Автоматического
переключения на другой профиль и скрытого отключения блока нет.

Если проверка с принудительной привязкой к карте не прошла, разрешен один проверяемый запасной путь для того же
адреса и профиля без нее, в пределах общего срока. Только настоящий ответ через ядро разрешает такой путь сессии;
после создания TUN остается обычная проверка связи, а выход sing-box ограничен точным IP + портом сервера. Настройки
TLS, DNS, IPv6 и набор правил брандмауэра не ослабляются. Реальные тесты проверяют несуществующее имя интерфейса,
верные/неверные данные доступа и сохранение быстрого привязанного пути, когда он работает. Цена fallback — возможный
дополнительный проход зашифрованного потока через sing-box и влияние на счетчики скорости.

Последующее уточнение пользователя: другой работающий клиент — Hiddify, TLS-фрагментация выключена. Это совпадает
с объяснением числа профилей через серверную политику User-Agent, но не устанавливает причину TCP-отказа. Проверка
официальных Go/Xray не выявила ошибки IPv4-индекса или Unicode-имени; RAW TCP и XHTTP учитывают SocketSettings.
Запасной путь привязки улучшает устойчивость, не выдается за доказанный диагноз.

### Отдельный воспроизведенный дефект Linux

В новой матрице настоящего HTTPS воспроизвелось повреждение TLS 1.3 при Vision + VPN + TLS-фрагментации. Прямой
контроль и XHTTP проходили; проблема исчезла при отключении Linux splice только у клиентского Xray. Узкое исправление
в `CoreProcess` сохраняет фрагментацию и TLS, меняя способ копирования в несовместимой цепочке. Проверенные источники
и граница окружения — [реестр](../../sources/REUSE_REGISTER.md#xray-vision-фрагментация-и-linux-splice--2026-11-02).
Это не установленная причина обрыва на Windows 10: Linux splice там не используется, а настройки пользователя
TLS-фрагментации в прежних материалах отсутствуют.

Окончательно закрывать исходный инцидент можно после проверки новой сборки на той же Windows 10 и раздаче iPhone:
TCP Vision и XHTTP отдельно, свежая ошибка вместо ожидания без объяснения, отсутствие позднего TUN после отключения,
сохранение блока при реальном обрыве. Общие проверки CI и локальные loopback-тесты не заменяют этот результат.

## Дополнение: сеть отключена, попытки продолжаются

Пользователь прислал фотографию сборки 0.1.0: одновременно показаны «Переподключение», «попытка 101», «Нет сети» и
включенный Kill Switch. Это не доказывает зависание одной попытки: политика `Backoff60Seconds` повторяет без общего
лимита, 60 секунд — максимальная пауза. Код до этого исправления запускал `RestartAsync` даже при известном
отсутствии внешней сети, а заголовок и кольцо определял только по `Reconnecting`. Это отдельный установленный дефект
ожидания и объяснения состояния; он не устанавливает исходную причину отказа TCP Vision.

Решение 553: служба передает отдельный подтвержденный признак `NetworkUnavailable`; при его наличии ожидает сеть,
сохраняя защиту, без роста попыток и новых ядер. Главное сообщение — «Нет сети», кольцо остановлено; одно уведомление
и постоянный баннер объясняют блокировку и восстановление. Режим «До 5 минут» ограничивает и ожидание сети; после
истечения нужен ручной повтор. Возврат сети не отменяет уже выполненное отключение или замену сессии. Неизвестная
сеть и отсутствие поля в старом IPC не выдаются за подтвержденное отсутствие адаптера.

Ручная проверка новой сборки на Windows остается открытой: пункты 11–12
[чеклиста](../../testing/windows-check.md#11-раздача-iphone-подписка-и-поздний-запуск-туннеля-2026-11-02).

В [CI коммита c75caec](https://github.com/rvburov/private-gateway-client/actions/runs/41471612528) новые сценарии
ожидания сети прошли на трех ОС. Windows и macOS выявили старую нестабильную проверку отказа от ненужной паузы:
она требовала роста числа попыток после фиксированных 3 секунд. Теперь счетчик соответствует настоящему запуску,
который включает остановку ядра, проверку и backoff. Тест ожидает фактический прогресс той же сессии через
`WatchStatus` в стандартном ограниченном ожидании и проверяет отсутствие паузы. Увеличения sleep, повторов упавшего
теста и пропусков не добавлено; код приложения в этом последующем исправлении теста не меняется.

## Дополнение 2026-11-05: запуск компьютера, автозапуск и блок при обрыве

Пользователь прислал два снимка сборки 0.1.0 (Windows 10, раздача iPhone) и описал порядок: компьютер включается,
программа стартует автозапуском и сразу включает защиту с блоком при обрыве, интернет (Wi-Fi раздачи) появляется
следом — и подключение иногда так и не поднимается. Статус: зафиксировано, не проверено; разработка — по команде.

| Снимок | Что видно | Вопрос |
| --- | --- | --- |
| XHTTP | «Переподключение… К тому же серверу · попытка 130», Wi-Fi подключен; «Весь трафик — поднимается», «Трафик на паузе до восстановления»; в списке сетей Windows у iPhone — «Нет подключения к Интернету, защищено»; IP — «Нет доступа, пока туннель не готов», строки реального IP нет | Почему при появившейся сети 130 попыток подряд не удались и почему пауза между ними не объясняет причину |
| TCP Vision | «Не удалось подтвердить связь через «rb-gateway · TCP Vision». Интернет заблокирован до успешного подключения VPN. Попытки продолжаются; можно сменить сервер», «попытка 1», реальный IP показан | Сервер недоступен, ссылка устарела или не готова локальная сеть — из окна не понять |

Подпись Windows «Нет подключения к Интернету» сама по себе ожидаема: проверка сети Windows (NCSI) идет мимо туннеля, и
блок ее режет. Но пользователь видит ее как «интернета нет вообще» — это нужно объяснять в окне.

Что проверить:

- **Сеть появилась после службы.** При старте с блоком и без адаптера служба ждет сеть (решение 553). Когда Wi-Fi
  подключается позже, туннель должен строиться заново на новом интерфейсе: маршрут до сервера, исключение сервера из
  блока, DNS для имени сервера (если адрес — имя). Проверить, что ни одно из них не осталось от состояния «сети нет» —
  130 одинаковых неудач указывают на устойчивую причину, а не на случайность.
- **Работает ли ссылка сервера.** Окно должно различать: нет ответа сервера (TCP/TLS до порта), сервер ответил, но
  профиль не принят (REALITY, UUID, flow), сервер работает, но через него нет выхода. Сейчас это одна фраза «не удалось
  подтвердить связь». Нужна проверка профиля, видимая пользователю, без открытия интернета мимо блока: разрешено только
  соединение до адреса сервера, как и для подключения.
- **Сравнение с другим профилем и с выключенным блоком** на той же раздаче — чтобы отделить сервер от порядка запуска.
- **Отчет проверки** сразу после неудачной серии: причина каждой попытки, интерфейс, адрес сервера (маскированный),
  время появления сети относительно старта службы.

Ручная последовательность добавить в [Windows, раздел 11](../../testing/windows-check.md#11-раздача-iphone-подписка-и-поздний-запуск-туннеля-2026-11-02):
перезагрузка с автозапуском и блоком, Wi-Fi раздачи включается через 1–2 минуты после входа.
