# Проверка режима VPN на вашей Windows

Что проверяется только на настоящей машине: полный маршрут через TUN, браузеры и программы, LLMNR в Wi-Fi,
пересылка трафика WSL, Hyper-V и хот-спота, контейнеры Docker. В CI это проверить нельзя: машина CI потеряла бы
связь с GitHub, а WSL, Hyper-V и Wi-Fi на ней нет. Пункты ROADMAP этапа 3 «Проверка на Windows с TUN»,
«Блок при обрыве для перенаправленного трафика» и «Контейнеры Windows за WinNAT» закрываются по итогам этой проверки.

CI уже проверяет без вас: правила WFP блока при обрыве (настоящие фильтры для curl), адаптер «Private Gateway» с DNS
туннеля (172.19.0.2, а если 172.19.0.1 на машине CI занят — второй адрес подсети, которую выбрала служба, решение 473),
путь TUN → Xray → сервер и FakeDNS — на узком маршруте, только для адресов теста (`WindowsTunnelTests`, решение 438).

Адреса серверов, ключи и ссылки в ответ не присылайте: в итогах достаточно «совпал с IP на «Главной» — да или нет».

## Подготовка (один раз)

1. Windows 10 или 11, учетная запись администратора. Git (с ним Git Bash) и .NET 10 SDK — в PowerShell:
   `winget install Git.Git Microsoft.DotNet.SDK.10`.
2. В Git Bash (репозиторий уже скачан — вместо первых двух строк `cd private-gateway-client && git checkout master &&
   git pull`):

   ```bash
   git clone https://github.com/rvburov/private-gateway-client.git
   cd private-gateway-client
   scripts/get-xray.sh && scripts/get-singbox.sh
   dotnet build PrivateGateway.slnx
   dotnet run --project desktop/src/Client.UI
   ```

3. В окне: «Начать» → «Установка службы» → «Установить» → в окне Windows «Да» → «Продолжить».
4. «Добавить сервер» → «Ввести ссылку» → ссылка вашего сервера → «Проверить» → «Добавить 1 сервер».
5. «Настройки» → «Режим» — «VPN · вся система»; «Блок при обрыве (Kill Switch)» — включен.
6. «Настройки» → «Защита и утечки»: «DNS в туннеле» — «По умолчанию: Cloudflare», «Блокировать IPv6 вне туннеля» — включен,
   «Разрешить локальную сеть» — выключен, «FakeDNS» — выключен.
7. «Главная» → кнопка щита. Дождаться «IP скрыт», нажать «Показать IP» — это IP сервера для сверки ниже.

## 1. Адаптер и DNS

В Git Bash:

```bash
ipconfig //all | grep -A12 "Private Gateway"
nslookup example.com 172.19.0.2
```

Ожидается: у адаптера «Private Gateway» адрес 172.19.0.1 и «DNS-серверы» 172.19.0.2; `nslookup` отвечает адресом.
Если 172.19.0.1 уже занят другим адаптером (Hyper-V, WSL, Docker, другой VPN-клиент), служба берет другую подсеть —
адрес 10.255.253.1 и DNS 10.255.253.2 (в «Проверке» → журнал: «Адрес TUN 172.19.0.1/30 занят другим адаптером»); тогда
здесь и ниже вместо 172.19.0.2 — адрес из строки «DNS-серверы».

Затем «Защита и утечки» → «FakeDNS» — включить, снова `nslookup example.com 172.19.0.2`. Ожидается адрес
198.18.x.x или 198.19.x.x. Выключить «FakeDNS».

## 2. Браузеры

В каждом браузере открыть https://browserleaks.com/dns, https://browserleaks.com/webrtc и https://test-ipv6.com:

| Браузер | Настройка |
| --- | --- |
| Chrome | как есть |
| Edge | «Параметры» → «Конфиденциальность» → «Использовать безопасный DNS» — включено, затем выключено |
| Firefox | «Настройки» → «Приватность и защита» → «DNS через HTTPS» → «Максимальная защита» |

DNS-тест показывает внешние рекурсивные резолверы, а не настройки DNS адаптера и не доказательство пути пакетов.
Несколько IP одного сервиса и различающиеся ASN сами по себе не доказывают обход. Неожиданный домашний резолвер
требует проверки фактического маршрута; узнаваемый публичный бренд не доказывает, что запрос прошел через VPN.
Ожидается: browserleaks/webrtc — IP как на «Главной», вашего реального IP нет; test-ipv6.com — IPv6 нет (при «Блокировать IPv6
вне туннеля»).

## 3. Программы

```bash
curl -s https://1.1.1.1/cdn-cgi/trace | grep ip=
git clone --depth 1 https://github.com/git/git.git /tmp/pg-check-git && rm -rf /tmp/pg-check-git
```

В PowerShell (его сетевой стек свой):

```powershell
(Invoke-WebRequest https://1.1.1.1/cdn-cgi/trace -UseBasicParsing).Content
```

Ожидается: `ip=` совпадает с IP на «Главной»; `git clone` проходит. VS Code и Claude Code: открыть, войти,
выполнить любое действие с сетью (расширения, запрос к Claude) — работают, на «Проверка» → «Весь трафик» — «через
туннель».

## 4. Блок при обрыве выключен

«Настройки» → «Блок при обрыве (Kill Switch)» — выключить.

1. В «IP скрыт» повторить пункты 1–3: утечек нет так же.
2. Обрыв: «Диспетчер задач» → «Подробности» → `xray.exe` → «Снять задачу». Пока на «Главной» «Переподключение»,
   открыть любой сайт: при выключенном блоке сайт открывается (сеть открыта — так и задумано). Дождаться
   «IP скрыт».
3. Включить блок обратно и повторить снятие `xray.exe`: во время «Переподключения» сайты не открываются.

## 5. LLMNR при разрешенной локальной сети

«Защита и утечки» → «Разрешить локальную сеть» — включить. В PowerShell от администратора:

```powershell
pktmon filter add -p 5355
pktmon start --etw -c
Resolve-DnsName pg-check-llmnr -LlmnrOnly
pktmon stop
pktmon format PktMon.etl -o llmnr.txt
pktmon filter remove
Select-String -Path llmnr.txt -Pattern "5355" | Measure-Object
```

Ожидается: `Resolve-DnsName` не находит имя, а пакетов на порт 5355 через адаптер Wi-Fi нет (`Count` — 0 или только
строки адаптера «Private Gateway»). Выключить «Разрешить локальную сеть».

## 6. Раздельный режим

«Настройки» → «Маршрутизация» → «Раздельный режим» → «Добавить программу» → Firefox. В Firefox
https://browserleaks.com/ip — ваш реальный IP, в Chrome — IP с «Главной». Вернуть «Весь трафик».

## 7. Пересылка: WSL, Hyper-V, хот-спот

Под защитой («IP скрыт»):

- WSL: `wsl curl -s https://1.1.1.1/cdn-cgi/trace | grep ip=` — IP с «Главной».
- Docker в WSL (контейнеры Linux): в Ubuntu `docker run --rm curlimages/curl -s https://1.1.1.1/cdn-cgi/trace | grep ip=` —
  IP с «Главной».
- ВМ Hyper-V: в браузере ВМ https://browserleaks.com/ip — IP с «Главной».
- Хот-спот: «Параметры Windows» → «Сеть и Интернет» → «Мобильный хот-спот» — включить, подключить телефон, на
  телефоне https://browserleaks.com/ip — IP с «Главной».

Затем блок при обрыве включен и обрыв, как в пункте 4.3 (снять `xray.exe`): пока «Переподключение», в WSL, контейнерах
Docker в WSL, ВМ и на телефоне сайты не открываются (ошибка или ожидание, а не ваш домашний IP). На Windows 10 правил
брандмауэра Hyper-V для WSL нет (они с Windows 11 22H2), а фильтры пересылки трафик WSL не видят: проверка 2026-11-06
показала, что при обрыве WSL на Windows 10 выходит напрямую. «Проверка» об этом предупреждает («Защита WSL2 и Hyper-V —
Недоступно»). Какой фильтр закрыл бы WSL — показывает проба в разделе 8а.

## 8. Контейнеры Windows за WinNAT (если стоит Docker Desktop)

Проверка отвечает на один вопрос: закрывает ли блок при обрыве интернет **контейнерам Windows** в Docker. Обычные
программы, WSL и виртуальные машины она не касается. Делать ее не обязательно (решение 2026-11-06, DECISIONS.md).

**Что нужно.** Docker Desktop, Git Bash и .NET 10 SDK, репозиторий — как в «Подготовке». Версию Windows узнать: Win+R →
`winver`. Проба сама выбирает образ контейнера под вашу Windows:

| Windows | Что делает проба |
| --- | --- |
| 11 Pro или Корпоративная, 24H2 и новее | образ `nanoserver:ltsc2025`, изоляция процессов |
| 11 Pro или Корпоративная, 21H2–23H2 | образ `nanoserver:ltsc2022`, изоляция процессов |
| 10 Pro или Корпоративная, 1809–22H2 | образ `nanoserver:ltsc2019`, изоляция Hyper-V: контейнер идет в маленькой виртуальной машине, но в сеть выходит через тот же WinNAT |
| «Домашняя» (10 или 11) | контейнеров Windows нет — проверять нечего, Docker там работает только с контейнерами Linux через WSL2 (раздел 7) |
| любая, Docker в WSL (Ubuntu и т. п.) или Docker Desktop с контейнерами Linux | проба не нужна: это контейнеры Linux в виртуальной машине WSL2, их трафик идет путем WSL — проверка в разделе 7 |

На Windows 10 Docker при переключении попросит включить компонент «Hyper-V» — это нужно для изоляции Hyper-V.

**Что происходит во время пробы.** Около минуты Windows закрывает пересылку на всю машину: в это время у WSL, виртуальных
машин и контейнеров нет сети. Браузер и обычные программы работают. В конце проба сама снимает свои фильтры. Если проба
прервется на середине (закрыли окно, выключился свет) — перезагрузите компьютер: фильтры пробы при перезагрузке
снимаются.

1. **Private Gateway**: щит на «Главной» → «Выключено». Проба ставит те же фильтры, что и программа, и снимет их.
   Если в «Настройки» → «Защита и утечки» включен «Строгий режим» — выключите его на время пробы: иначе сеть останется
   закрытой и без VPN. Окно можно не закрывать (пункт трея «Закрыть интерфейс» закрывает только окно, служба работает).
2. **Docker Desktop**: значок кита в трее → «Switch to Windows containers…» → «Switch». Если Docker попросит включить
   компоненты Windows «Containers» и «Hyper-V» — согласитесь и перезагрузите компьютер, затем снова этот шаг.
3. **Git Bash от администратора**: «Пуск» → «Git Bash» → правой кнопкой → «Запуск от имени администратора». В нем:

   ```bash
   cd /c/путь/к/private-gateway-client
   git checkout master && git pull
   PG_FORWARD_PROBE=1 dotnet test --project desktop/tests/Network --ignore-exit-code 8 -- --filter-method "*Probe_container_behind_nat_and_the_forward_filters"
   ```

   Первый запуск скачивает образ `nanoserver` (120–300 МБ) — несколько минут; на Windows 10 первый запуск контейнера
   в изоляции Hyper-V тоже дольше обычного.
4. Итог — в файле `artifacts/forward-probe.txt` в папке репозитория (`cat artifacts/forward-probe.txt`). Пришлите его
   текст: там только адрес github.com и строки ниже, своих адресов и ключей в нем нет.
   - «блок без туннеля (пересылка закрыта): контейнер закрыт» — блок закрывает такие контейнеры, все в порядке;
   - «… контейнер ПРОХОДИТ — пересылку WinNAT фильтры не видят» — не закрывает: нужна доработка;
   - «после снятия: контейнер проходит» — проба за собой убрала;
   - «после снятия: контейнер НЕ ПРОХОДИТ» — перезагрузите компьютер и напишите об этом.

   Первая строка файла — версия Windows, образ и изоляция: по ним видно, какая конфигурация проверена. Если файла нет, а
   тест «пропущен», пришлите строку с причиной из окна (например, «нет docker», «контейнер не выходит в сеть и без
   блока»).
5. **Вернуть как было**: Docker Desktop → значок кита → «Switch to Linux containers…» (если раньше были они). Запустите
   Private Gateway и включите защиту.

## 8а. Проба утечки WSL при обрыве (Windows 10)

Проба отвечает на один вопрос: каким фильтром Windows можно закрыть интернет WSL, когда VPN оборвался. Ее итог нужен,
чтобы доработать блок при обрыве на Windows 10. Делать ее можно только на компьютере, где стоит WSL (Ubuntu и т. п.).

**Что происходит во время пробы.** Проба по очереди ставит шесть фильтров Windows (по одному на каждый слой) — каждый
закрывает **только адрес 1.1.1.1**, остальной интернет машины работает. С каждым фильтром проба спрашивает 1.1.1.1 из WSL и
из самой Windows и снимает фильтр. Всего около минуты. Фильтры пробы не переживают перезагрузку: если проба прервется на
середине — перезагрузите компьютер.

1. **Private Gateway**: щит на «Главной» → «Выключено». Если в «Настройки» → «Защита и утечки» включен «Строгий режим» —
   выключите его на время пробы: иначе сеть останется закрытой и без VPN. Окно можно не закрывать.
2. **WSL**: запустите один раз Ubuntu («Пуск» → «Ubuntu») и проверьте, что в ней есть curl: `curl --version`. Нет —
   `sudo apt install -y curl`. Окно Ubuntu можно закрыть.
3. **Git Bash от администратора**: «Пуск» → «Git Bash» → правой кнопкой → «Запуск от имени администратора». В нем:

   ```bash
   cd /c/rvburov/private-gateway-client
   git checkout master && git pull
   PG_WSL_PROBE=1 dotnet test --project desktop/tests/Network --ignore-exit-code 8 -- --filter-method "*Probe_wsl_behind_winnat_by_wfp_layer"
   ```

4. Итог — в файле `artifacts/wsl-probe.txt` (`cat artifacts/wsl-probe.txt`). Пришлите его текст: в нем только версия
   Windows, адрес 1.1.1.1 и строки вида «исходящие IP-пакеты (OUTBOUND_IPPACKET): WSL закрыта, Windows закрыта».
   - «без фильтров: WSL проходит» — WSL в сети, проба имеет смысл;
   - «…: WSL закрыта» — этот слой закрывает WSL: им и доработается блок;
   - «…: WSL ПРОХОДИТ» — этот слой трафик WSL не видит;
   - «после снятия: WSL проходит» — проба за собой убрала; «НЕ ПРОХОДИТ» — перезагрузите компьютер и напишите об этом.

   Если файла нет, а тест «пропущен», пришлите строку с причиной из окна (например, «WSL не выходит к 1.1.1.1 и без
   фильтров»).
5. Включите защиту, а «Строгий режим» — снова, если выключали его в шаге 1.

## 9. Интерфейс (правки 28 и 29.10.2026)

Перед этим — свежий код: в Git Bash `git pull`, `scripts/get-xray.sh` (ядро обновилось до 26.10.21), `dotnet build
PrivateGateway.slnx`, `dotnet run --project desktop/src/Client.UI`, затем «Настройки» → «О программе» → «Обновить службу».

1. Нижнее меню: «Главная», «Серверы», «Проверка», «Настройки» — целиком внутри белой плашки, не у самого края.
2. «Главная», навести указатель на плитку «Весь трафик» (и на другие): рамка и фон — того же цвета, что плитка, ярче;
   серой плитка не становится. Нажать на плитку — рамка остается, под плитками — объяснение.
3. Навести на кнопку щита: кольцо и знак — прежнего цвета (красные, при защите — зеленые), внутри — тот же цвет,
   прозрачный; знак не чернеет, кольцо не пропадает.
4. Справа от сервера — «Сменить» в рамке, как списки в «Подключении и ядре»; при наведении — синие текст и рамка,
   строка сервера не сереет. Нажать — список серверов шириной по названиям.
5. «Настройки» → «Подключение и ядро» → «Журнал ядра» (и другие списки): список шириной по тексту, выбранный пункт —
   синим полужирным, при наведении пункт — синим текстом без серой заливки.
6. «Настройки» → «Для опытных», «Проверка» (блок «Сеть машины» и «Лаборатория»), «О программе» → ссылки внизу:
   стрелки «›» у правого края, в каждом блоке на одной линии, а не сразу за текстом; при наведении на строку стрелка
   синеет вместе с заголовком. Строки «Для опытных» и ссылки «О программе» разделены полосами.
7. «Настройки» → «Резервная копия»: флажки — галочка мелкая, по центру синего квадрата, как в макете.
8. «Проверка» → прокрутить вниз → «Как меняется путь при VPN» → «Назад»: «Проверка» на том же месте, а не в начале.
9. «Настройки» → «Блок при обрыве» — выключить → «Оставить включенным»: переключатель остается включенным. То же
   «Защита и утечки» → «Строгий режим» → «Отмена».
10. «Серверы» → кнопка фильтра справа в поиске → нажать на другой сервер под панелью: панель закрывается, выбранный
    сервер не меняется.

## 10. Панель и другие службы на IP VPN-сервера (решение 512)

Нужен VPN-сервер и HTTPS-панель на том же IP, но другом порту, которая уже открывается без VPN.
Обезличенный пример: транспорт `198.51.100.20:8444`, панель `https://example.com:8443/`; в проверке
используйте свой адрес, не пример. Ключи и ссылки профиля в отчет не включайте.

1. После обновления программы и службы проверьте панель без VPN: она открывается с действительным
   сертификатом. Не открывается уже здесь — этот сценарий пока не различает ошибку клиента и недоступность сайта.
2. Подключитесь к тому же серверу через XHTTP, дождитесь «IP скрыт» и откройте ту же панель в браузере.
   Ожидается: панель открывается; ее порт не обязан совпадать с портом VPN-профиля.
3. Не отключая VPN, в «Настройках» временно выключите «Блок при обрыве» и обновите панель: она также
   открывается. Затем включите блок обратно. Правила «только туннель» при работающем VPN сохраняются в обоих случаях.
4. Запишите результаты отдельно: панель без VPN, с XHTTP и блоком, с XHTTP без блока. Открытие страницы
   проверяет доступность, а не отсутствие утечек или полный маршрут всех программ.

Для исправления добавлены код и регрессионные тесты: только транспортная пара IP + порт получает прямой
выход; другие порты этого IP остаются в TUN → Xray. Локально: 1505 тестов прошли, 0 ошибок, 117 пропусков
с причинами среды; два мутанта маршрутизации пойманы. CI пока не подтвержден,
на Windows пользователя исправление не проверено. До результатов этих проверок случай не считается закрытым.

## 11. Раздача iPhone, подписка и поздний запуск туннеля (2026-11-02)

Связанный [разбор инцидента](../operations/incidents/2026-11-02-windows-hotspot.md) остается открытым. Здесь порядок
сравнения, а не выполненная проверка и не универсальное исправление настройками.

1. Запишите версии и коммиты окна и службы. Сохраните исходные значения «Подключение и ядро» и «Защита и утечки».
   Другой VPN выключен; во всех случаях — та же раздача и тот же профиль. При остаточных попытках сначала один раз
   перезагрузите Windows. После каждой попытки отключайте VPN и ждите 20 с; частыми нажатиями новые попытки не создавайте.
2. **Прокси:** «Настройки» → «Режим» → «Только прокси», подтвердите переход. В «Подключение и ядро» включите
   «Системный прокси», подключитесь, дождитесь «Применен: 127.0.0.1:порт». Проверьте сайт в браузере и явным запросом
   ниже (порт замените, если в настройках другой). Режим покрывает только использующие прокси приложения, не весь ПК.

   ```bash
   curl.exe --proxy http://127.0.0.1:10808 --noproxy localhost --connect-timeout 10 --max-time 20 --head https://example.com
   ```

   Сохраните весь вывод, включая ошибку после `200 Connection established`, если она есть: ответ локального прокси
   еще не подтверждает ответ сайта. Проверки службы в этом режиме частично идут напрямую и не заменяют этот запрос.
3. **VPN 1420:** отключитесь; верните «VPN · вся система», установите MTU 1420. Для этого сравнения системный прокси
   в режиме VPN выключите: его значение хранится отдельно от прокси-режима. Иначе браузер может миновать TUN через
   локальный вход. Перезапустите браузер; для запроса без влияния env-прокси:

   ```bash
   curl.exe --noproxy "*" --connect-timeout 10 --max-time 20 --head https://example.com
   ```

4. **VPN 1280:** если отказ остался, отключитесь и измените только MTU на 1280; повторите предыдущую проверку.
   Стек TUN, отпечаток TLS, Mux, фрагментацию, строгие маршруты и защиты между этими попытками не меняйте.
5. В каждом случае нажмите «Проверка» → «Проверить» один раз и сохраните «Экспорт отчета» с пометкой режима и MTU.
   В исправленной сборке результаты показываются отдельно от задержки; каждый из этих этапов ограничен 30 с.
   Если проверка не завершилась, экспортируйте как есть, запишите время и состояние. Повторное нажатие просит еще
   один прогон, а смена сессии отменяет старые запросы. Результаты замера и новые строки журнала в отчете могут
   относиться к разным моментам.
6. **Подписка:** запишите точное сообщение/код и момент ошибки, отдельно для первоначального добавления,
   «Обновить» сохраненную подписку и подключения TCP Vision. Запишите, включено ли «Обновлять только через VPN»,
   состояние VPN в этот момент, число групп и профилей в предпросмотре; проверьте, сохранился ли прежний список после
   ошибки. URL, QR, ключи, UUID и тело подписки не присылайте. Запрет VPN-only в режиме прокси или без VPN — отдельный
   результат, а не подтверждение недействительного URL. Самостоятельно ослаблять эту политику как исправление нельзя.
7. **Жизненный цикл:** при отмене подключения запишите время «Выключено» и последующие события ядра. После завершения
   отключения прежняя попытка не должна запускать TUN и менять сеть. До исправления HS-02 это проверка известного
   дефекта, а не рекомендация многократно включать и выключать защиту.
8. Для зависания/закрытия окна запишите точное время и текст события Windows Application Error, .NET Runtime или
   Application Hang, если оно появилось. Сетевой тайм-аут и долгое «Проверяется» сами не являются стеком падения.
   После проверки восстановите исходные настройки; диагностические изменения не выдаются за постоянную рекомендацию.
9. **Первый отказ и уведомление:** из открытой сети, без сохраненного блока, выберите заведомо недоступный тестовый
   профиль, в том числе с прежним «нет». Ожидается свежая проверка в пределах таймаута подключения (по умолчанию
   10 с), затем понятный отказ и «Сменить сервер» на главной; новые TUN и правила не включаются, обычный интернет
   остается доступен. Если уже стоял Kill Switch/строгий блок, он остается закрытым: уведомление должно говорить об
   этом, а не обещать прямую сеть. Старое «нет» у восстановившегося профиля не запрещает повторную проверку.
10. **Обрыв после успеха:** у своего тестового сервера прервите соединение. Ожидается сообщение о фактической
    блокировке до возвращения VPN и постоянное действие смены сервера; новые автоматические попытки не спамят,
    явная ручная попытка не подавляется старым уведомлением. Проверьте TCP Vision и XHTTP отдельно. Название
    другого клиента и выключенная TLS-фрагментация сами по себе не устанавливают причину отказа.

11. **Сеть отключена физически:** после успешного VPN выключите внешний Wi-Fi/отсоедините кабель так, чтобы не осталось
    другой внешней сети. После события ОС главная и кнопка показывают «Нет сети», кольцо не вращается; одно уведомление
    и постоянный баннер объясняют ожидание и фактическую блокировку. Счетчик попыток не растет, новые ядра не запускаются.
    Включите сеть: подключение к тому же профилю возобновляется без нового ручного выбора и без снятия Kill Switch.
    Затем проверьте «Отключить» во время ожидания: возвращение сети не должно вновь включить VPN. Наличие Wi-Fi без
    доступа к провайдеру отдельно проверяется через профиль; само наличие адаптера не доказывает доступ в интернет.
12. **Лимит ожидания:** «Настройки» → «Подключение и ядро» → «Переподключение» → «До 5 минут». Снова отключите внешнюю
    сеть и дождитесь лимита от момента потери VPN: автоматические попытки прекращаются, текст предлагает повторить
    после восстановления. При включенном блоке интернет остается закрытым. В режиме «Экспоненц. до 60 с» общее
    ожидание не ограничено: 60 секунд — максимальная пауза между попытками при наличии сети. Верните исходную настройку.

Ожидаемый набор: отчеты «прокси», «VPN 1420», при необходимости «VPN 1280»; результат сайта/команды и время обрыва
по каждому; исходные настройки; текст ошибки подписки; название и версия работающего другого клиента. Не нужны
полный `ipconfig`, реальные публичные адреса, ссылки и дамп всех переменных окружения.

## 12. DNS: настройка, политика и измерение (2026-11-04)

1. Сверьте версии и сборки окна и службы. В «Настройки» → «Защита и утечки» прежний выбор «Из профиля» теперь
   явно называет Cloudflare. После перезапуска выбранные Quad9 и свой DNS также сохраняются.
2. В режиме VPN проверьте отдельно выбранный DNS и состояние защиты службы. На «Главной» DNS-плитка описывает
   политику, а не обещает отсутствие всех утечек. Измененный выбор до переподключения не должен выдаваться за
   параметры действующей сессии.
3. На «Проверке» прямой DNS-ответ означает доступный IPv4 UDP/53 вне туннеля. При отсутствии ответа или недоступной
   пробе ожидается неподтвержденный результат с областью проверки; это не «все проверки успешны» и не бесконечное
   «Проверяется». Ради положительного результата не отключайте защиту.
   Если ранее был подтвержден открытый путь, следующий замер без ответа не должен стирать это предупреждение;
   состояние защиты и результат последней пробы могут различаться.
4. При режиме «Только прокси» пояснение должно прямо говорить, что DNS всей Windows не перехватывается.
   Браузерный DoH может выбирать свой сервис; FakeDNS не делает резолвер невидимым внешнему тестеру.
5. Сохраните отчет. В отдельном разделе DNS должны быть выбор в настройках, режим службы, FakeDNS, число выбранных
   исключений, состояние защиты и результат пробы. Собственный DNS описывается типом, без URL/учетных данных.
   DNS-адреса адаптера/TUN подписаны как сведения ОС, а не найденные внешние рекурсивные резолверы.
6. Браузерный DNS-тест оценивайте отдельно: несколько IP одного сервиса нормальны, различие ASN не доказывает
   маршрут. Если виден неожиданный резолвер, зафиксируйте одинаковые настройки и подтвердите фактический путь
   дополнительным наблюдением на своем компьютере; узнаваемый публичный бренд тоже не доказывает VPN-путь.

Результат ручной проверки и обезличенный отчет фиксируются отдельно от CI. Сценарии открытого обхода,
запоздалого ответа и отмены проверяются управляемыми автоматическими стендами; серверные DNS и браузеры
не перенастраиваются автоматически.
