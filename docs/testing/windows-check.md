# Проверка режима VPN на вашей Windows

Что проверяется только на настоящей машине: полный маршрут через TUN, браузеры и программы, LLMNR в Wi-Fi,
пересылка трафика WSL, Hyper-V и хот-спота, контейнеры Docker. В CI это проверить нельзя: машина CI потеряла бы
связь с GitHub, а WSL, Hyper-V и Wi-Fi на ней нет. Пункты ROADMAP этапа 3 «Проверка на Windows с TUN»,
«Блок при обрыве для перенаправленного трафика» и «Контейнеры Windows за WinNAT» закрываются по итогам этой проверки.

CI уже проверяет без вас: правила WFP блока при обрыве (настоящие фильтры для curl), адаптер «Private Gateway» с DNS
туннеля (172.19.0.2, а если 172.19.0.1 на машине CI занят — второй адрес подсети, которую выбрала служба, решение 473),
путь TUN → Xray → сервер и FakeDNS — на узком маршруте, только для адресов теста (`WindowsTunnelTests`, решение 438).

Адреса серверов, ключи и ссылки в ответ не присылайте: в итогах достаточно «совпал с IP на «Главной» — да или нет».

## Подготовка (один раз)

1. Windows 10 или 11, учетная запись администратора. Git (с ним Git Bash) и .NET 10 SDK — в PowerShell:
   `winget install Git.Git Microsoft.DotNet.SDK.10`.
2. В Git Bash (репозиторий уже скачан — вместо первых двух строк `cd private-gateway-client && git checkout master &&
   git pull`):

   ```bash
   git clone https://github.com/rvburov/private-gateway-client.git
   cd private-gateway-client
   scripts/get-xray.sh && scripts/get-singbox.sh
   dotnet build PrivateGateway.slnx
   dotnet run --project desktop/src/Client.UI
   ```

3. В окне: «Начать» → «Установка службы» → «Установить» → в окне Windows «Да» → «Продолжить».
4. «Добавить сервер» → «Ввести ссылку» → ссылка вашего сервера → «Проверить» → «Добавить 1 сервер».
5. «Настройки» → «Режим» — «VPN · вся система»; «Блок при обрыве (Kill Switch)» — включен.
6. «Настройки» → «Защита и утечки»: «DNS в туннеле» — «Из профиля», «Блокировать IPv6 вне туннеля» — включен,
   «Разрешить локальную сеть» — выключен, «FakeDNS» — выключен.
7. «Главная» → кнопка щита. Дождаться «IP скрыт», нажать «Показать IP» — это IP сервера для сверки ниже.

## 1. Адаптер и DNS

В Git Bash:

```bash
ipconfig //all | grep -A12 "Private Gateway"
nslookup example.com 172.19.0.2
```

Ожидается: у адаптера «Private Gateway» адрес 172.19.0.1 и «DNS-серверы» 172.19.0.2; `nslookup` отвечает адресом.
Если 172.19.0.1 уже занят другим адаптером (Hyper-V, WSL, Docker, другой VPN-клиент), служба берет другую подсеть —
адрес 10.255.253.1 и DNS 10.255.253.2 (в «Проверке» → журнал: «Адрес TUN 172.19.0.1/30 занят другим адаптером»); тогда
здесь и ниже вместо 172.19.0.2 — адрес из строки «DNS-серверы».

Затем «Защита и утечки» → «FakeDNS» — включить, снова `nslookup example.com 172.19.0.2`. Ожидается адрес
198.18.x.x или 198.19.x.x. Выключить «FakeDNS».

## 2. Браузеры

В каждом браузере открыть https://browserleaks.com/dns, https://browserleaks.com/webrtc и https://test-ipv6.com:

| Браузер | Настройка |
| --- | --- |
| Chrome | как есть |
| Edge | «Параметры» → «Конфиденциальность» → «Использовать безопасный DNS» — включено, затем выключено |
| Firefox | «Настройки» → «Приватность и защита» → «DNS через HTTPS» → «Максимальная защита» |

Ожидается: browserleaks/dns — только DNS-серверы со стороны сервера, ни одного DNS вашего провайдера;
browserleaks/webrtc — IP как на «Главной», вашего реального IP нет; test-ipv6.com — IPv6 нет (при «Блокировать IPv6
вне туннеля»).

## 3. Программы

```bash
curl -s https://1.1.1.1/cdn-cgi/trace | grep ip=
git clone --depth 1 https://github.com/git/git.git /tmp/pg-check-git && rm -rf /tmp/pg-check-git
```

В PowerShell (его сетевой стек свой):

```powershell
(Invoke-WebRequest https://1.1.1.1/cdn-cgi/trace -UseBasicParsing).Content
```

Ожидается: `ip=` совпадает с IP на «Главной»; `git clone` проходит. VS Code и Claude Code: открыть, войти,
выполнить любое действие с сетью (расширения, запрос к Claude) — работают, на «Проверка» → «Весь трафик» — «через
туннель».

## 4. Блок при обрыве выключен

«Настройки» → «Блок при обрыве (Kill Switch)» — выключить.

1. В «IP скрыт» повторить пункты 1–3: утечек нет так же.
2. Обрыв: «Диспетчер задач» → «Подробности» → `xray.exe` → «Снять задачу». Пока на «Главной» «Переподключение»,
   открыть любой сайт: при выключенном блоке сайт открывается (сеть открыта — так и задумано). Дождаться
   «IP скрыт».
3. Включить блок обратно и повторить снятие `xray.exe`: во время «Переподключения» сайты не открываются.

## 5. LLMNR при разрешенной локальной сети

«Защита и утечки» → «Разрешить локальную сеть» — включить. В PowerShell от администратора:

```powershell
pktmon filter add -p 5355
pktmon start --etw -c
Resolve-DnsName pg-check-llmnr -LlmnrOnly
pktmon stop
pktmon format PktMon.etl -o llmnr.txt
pktmon filter remove
Select-String -Path llmnr.txt -Pattern "5355" | Measure-Object
```

Ожидается: `Resolve-DnsName` не находит имя, а пакетов на порт 5355 через адаптер Wi-Fi нет (`Count` — 0 или только
строки адаптера «Private Gateway»). Выключить «Разрешить локальную сеть».

## 6. Раздельный режим

«Настройки» → «Маршрутизация» → «Раздельный режим» → «Добавить программу» → Firefox. В Firefox
https://browserleaks.com/ip — ваш реальный IP, в Chrome — IP с «Главной». Вернуть «Весь трафик».

## 7. Пересылка: WSL, Hyper-V, хот-спот

Под защитой («IP скрыт»):

- WSL: `wsl curl -s https://1.1.1.1/cdn-cgi/trace | grep ip=` — IP с «Главной».
- ВМ Hyper-V: в браузере ВМ https://browserleaks.com/ip — IP с «Главной».
- Хот-спот: «Параметры Windows» → «Сеть и Интернет» → «Мобильный хот-спот» — включить, подключить телефон, на
  телефоне https://browserleaks.com/ip — IP с «Главной».

Затем блок при обрыве включен и обрыв, как в пункте 4.3 (снять `xray.exe`): пока «Переподключение», в WSL, ВМ и на
телефоне сайты не открываются.

## 8. Контейнеры Windows за WinNAT (если стоит Docker Desktop с контейнерами Windows)

Под защитой и при обрыве (пункт 4.3):

```bash
docker run --rm --isolation=process mcr.microsoft.com/windows/nanoserver:ltsc2022 curl.exe -s https://1.1.1.1/cdn-cgi/trace
```

Ожидается: под защитой `ip=` — IP с «Главной»; во время «Переподключения» с включенным блоком — ошибка соединения.
Если во время обрыва контейнер выходит в сеть — это утечка, запишите. Подробный отчет пробы (Git Bash от
администратора):

```bash
PG_FORWARD_PROBE=1 dotnet test --project desktop/tests/Network -- --filter-method "*Probe_container_behind_nat_and_the_forward_filters"
```

## 9. Интерфейс (правки 28 и 29.10.2026)

Перед этим — свежий код: в Git Bash `git pull`, `scripts/get-xray.sh` (ядро обновилось до 26.10.21), `dotnet build
PrivateGateway.slnx`, `dotnet run --project desktop/src/Client.UI`, затем «Настройки» → «О программе» → «Обновить службу».

1. Нижнее меню: «Главная», «Серверы», «Проверка», «Настройки» — целиком внутри белой плашки, не у самого края.
2. «Главная», навести указатель на плитку «Весь трафик» (и на другие): рамка и фон — того же цвета, что плитка, ярче;
   серой плитка не становится. Нажать на плитку — рамка остается, под плитками — объяснение.
3. Навести на кнопку щита: кольцо и знак — прежнего цвета (красные, при защите — зеленые), внутри — тот же цвет,
   прозрачный; знак не чернеет, кольцо не пропадает.
4. Справа от сервера — «Сменить» в рамке, как списки в «Подключении и ядре»; при наведении — синие текст и рамка,
   строка сервера не сереет. Нажать — список серверов шириной по названиям.
5. «Настройки» → «Подключение и ядро» → «Журнал ядра» (и другие списки): список шириной по тексту, выбранный пункт —
   синим полужирным, при наведении пункт — синим текстом без серой заливки.
6. «Настройки» → «Для опытных», «Проверка» (блок «Сеть машины» и «Лаборатория»), «О программе» → ссылки внизу:
   стрелки «›» у правого края, в каждом блоке на одной линии, а не сразу за текстом; при наведении на строку стрелка
   синеет вместе с заголовком. Строки «Для опытных» и ссылки «О программе» разделены полосами.
7. «Настройки» → «Резервная копия»: флажки — галочка мелкая, по центру синего квадрата, как в макете.
8. «Проверка» → прокрутить вниз → «Как меняется путь при VPN» → «Назад»: «Проверка» на том же месте, а не в начале.
9. «Настройки» → «Блок при обрыве» — выключить → «Оставить включенным»: переключатель остается включенным. То же
   «Защита и утечки» → «Строгий режим» → «Отмена».
10. «Серверы» → кнопка фильтра справа в поиске → нажать на другой сервер под панелью: панель закрывается, выбранный
    сервер не меняется.

## 10. Панель и другие службы на IP VPN-сервера (решение 512)

Нужен VPN-сервер и HTTPS-панель на том же IP, но другом порту, которая уже открывается без VPN.
Обезличенный пример: транспорт `198.51.100.20:8444`, панель `https://example.com:8443/`; в проверке
используйте свой адрес, не пример. Ключи и ссылки профиля в отчет не включайте.

1. После обновления программы и службы проверьте панель без VPN: она открывается с действительным
   сертификатом. Не открывается уже здесь — этот сценарий пока не различает ошибку клиента и недоступность сайта.
2. Подключитесь к тому же серверу через XHTTP, дождитесь «IP скрыт» и откройте ту же панель в браузере.
   Ожидается: панель открывается; ее порт не обязан совпадать с портом VPN-профиля.
3. Не отключая VPN, в «Настройках» временно выключите «Блок при обрыве» и обновите панель: она также
   открывается. Затем включите блок обратно. Правила «только туннель» при работающем VPN сохраняются в обоих случаях.
4. Запишите результаты отдельно: панель без VPN, с XHTTP и блоком, с XHTTP без блока. Открытие страницы
   проверяет доступность, а не отсутствие утечек или полный маршрут всех программ.

Для исправления добавлены код и регрессионные тесты: только транспортная пара IP + порт получает прямой
выход; другие порты этого IP остаются в TUN → Xray. Локально: 1505 тестов прошли, 0 ошибок, 117 пропусков
с причинами среды; два мутанта маршрутизации пойманы. CI пока не подтвержден,
на Windows пользователя исправление не проверено. До результатов этих проверок случай не считается закрытым.

## 11. Раздача iPhone, подписка и поздний запуск туннеля (2026-11-02)

Связанный [разбор инцидента](../operations/incidents/2026-11-02-windows-hotspot.md) остается открытым. Здесь порядок
сравнения, а не выполненная проверка и не универсальное исправление настройками.

1. Запишите версии и коммиты окна и службы. Сохраните исходные значения «Подключение и ядро» и «Защита и утечки».
   Другой VPN выключен; во всех случаях — та же раздача и тот же профиль. При остаточных попытках сначала один раз
   перезагрузите Windows. После каждой попытки отключайте VPN и ждите 20 с; частыми нажатиями новые попытки не создавайте.
2. **Прокси:** «Настройки» → «Режим» → «Только прокси», подтвердите переход. В «Подключение и ядро» включите
   «Системный прокси», подключитесь, дождитесь «Применен: 127.0.0.1:порт». Проверьте сайт в браузере и явным запросом
   ниже (порт замените, если в настройках другой). Режим покрывает только использующие прокси приложения, не весь ПК.

   ```bash
   curl.exe --proxy http://127.0.0.1:10808 --noproxy localhost --connect-timeout 10 --max-time 20 --head https://example.com
   ```

   Сохраните весь вывод, включая ошибку после `200 Connection established`, если она есть: ответ локального прокси
   еще не подтверждает ответ сайта. Проверки службы в этом режиме частично идут напрямую и не заменяют этот запрос.
3. **VPN 1420:** отключитесь; верните «VPN · вся система», установите MTU 1420. Для этого сравнения системный прокси
   в режиме VPN выключите: его значение хранится отдельно от прокси-режима. Иначе браузер может миновать TUN через
   локальный вход. Перезапустите браузер; для запроса без влияния env-прокси:

   ```bash
   curl.exe --noproxy "*" --connect-timeout 10 --max-time 20 --head https://example.com
   ```

4. **VPN 1280:** если отказ остался, отключитесь и измените только MTU на 1280; повторите предыдущую проверку.
   Стек TUN, отпечаток TLS, Mux, фрагментацию, строгие маршруты и защиты между этими попытками не меняйте.
5. В каждом случае нажмите «Проверка» → «Проверить» один раз и сохраните «Экспорт отчета» с пометкой режима и MTU.
   Если за 90–120 с проверка не завершилась, экспортируйте как есть, запишите время и состояние. Повторное нажатие
   и смена состояния могут ставить еще один прогон в очередь. Результаты старого замера и новые строки журнала
   в отчете могут относиться к разным моментам.
6. **Подписка:** запишите точное сообщение/код и момент ошибки, отдельно для первоначального добавления,
   «Обновить» сохраненную подписку и подключения TCP Vision. Запишите, включено ли «Обновлять только через VPN»,
   состояние VPN в этот момент, число групп и профилей в предпросмотре; проверьте, сохранился ли прежний список после
   ошибки. URL, QR, ключи, UUID и тело подписки не присылайте. Запрет VPN-only в режиме прокси или без VPN — отдельный
   результат, а не подтверждение недействительного URL. Самостоятельно ослаблять эту политику как исправление нельзя.
7. **Жизненный цикл:** при отмене подключения запишите время «Выключено» и последующие события ядра. После завершения
   отключения прежняя попытка не должна запускать TUN и менять сеть. До исправления HS-02 это проверка известного
   дефекта, а не рекомендация многократно включать и выключать защиту.
8. Для зависания/закрытия окна запишите точное время и текст события Windows Application Error, .NET Runtime или
   Application Hang, если оно появилось. Сетевой тайм-аут и долгое «Проверяется» сами не являются стеком падения.
   После проверки восстановите исходные настройки; диагностические изменения не выдаются за постоянную рекомендацию.

Ожидаемый набор: отчеты «прокси», «VPN 1420», при необходимости «VPN 1280»; результат сайта/команды и время обрыва
по каждому; исходные настройки; текст ошибки подписки; название и версия работающего другого клиента. Не нужны
полный `ipconfig`, реальные публичные адреса, ссылки и дамп всех переменных окружения.
