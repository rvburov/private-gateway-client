# Связка ключей macOS: запуск, замер и отказ

Регрессия по отчету MacBook M4 от 2026-11-14: при старте окно запрашивало доступ к нескольким отдельным секретам,
замер списка снова читал ключ каждого сервера, а «Отказать» выходил необработанным исключением из команды обновления.
Проверка относится к macOS arm64 и x64; общий отказ хранилища проверяется также на Windows и Linux.

## Что изменилось

- `KeychainFileSecretStore` хранит отдельные секреты в `secrets.db` зашифрованными AES-256-GCM. Случайный 256-битный ключ
  находится в Связке ключей пользователя, запись `PrivateGateway.Vault / vault-master-v1`. Идентификатор записи входит в
  аутентифицируемые данные: перестановка двух шифров не открывает другой секрет.
- Успешно открытый ключ кешируется только в памяти текущего процесса; повторный замер и обновление уже перенесенных
  записей не читают пароль из Связки ключей для каждого сервера. При завершении контейнера приложения буфер ключа очищается.
- Прежние отдельные записи переносятся по обращению. Шифр и отметка незаконченной очистки записываются одной транзакцией;
  исходник удаляется только после успешной записи и проверки. Прерванная очистка продолжается при следующем обращении
  **без системных окон**. Если macOS требует отдельное разрешение на удаление старой записи, защищенный исходник остается
  в Связке ключей до следующей успешной уборки. Это не мешает использовать уже перенесенный секрет.
- Удаление сохраняет постоянную отметку вместе с удалением шифра. Даже если Связка ключей не разрешила убрать старую копию,
  приложение больше не читает ее после выхода из аккаунта или удаления сервера. Только явное сохранение нового значения
  снимает отметку. Обычная уборка не меняет права доступа к Связке ключей.
- Запрет системных окон действует только во время неинтерактивной уборки и восстанавливается в `finally`. Все нативные
  обращения сериализованы одним общим замком: параллельное чтение общего ключа не теряет возможность запросить разрешение.
- Отказ в доступе не означает «ключа нет» и не создает новый ключ. Добавление сервера также отказывает, если файл уже
  содержит секреты, а ключ утрачен. После отказа пользователь может повторить действие.
- Открытие списка с разными адресами подписок не читает их секреты ради поиска дублей. Отказ при необязательном переносе
  старых метаданных не мешает показать список. Неудачный замер/обновление прекращается с понятным сообщением.

**Граница обещания:** при первом переносе старых записей macOS может отдельно спросить доступ к каждой записи по ее
прежним правам. Программа не обходит эти права. После переноса нужен один ключ, однако количество системных диалогов
также зависит от блокировки Связки ключей и доверия macOS к текущей подписи приложения. Новая сборка с ad-hoc подписью
может снова потребовать разрешение. Не удалять Связку ключей и не разрешать доступ всем приложениям ради этой проверки.

Следует различать **первый перенос прежних отдельных записей** и **обновление уже перенесенного приложения**. Для первого
macOS сохраняет права каждого старого элемента: один ввод пароля разблокировки Связки ключей не отменяет их. После переноса
проверяется один общий ключ на процесс; повторный замер 30 серверов и новое обновление приложения не должны читать старые
пароли поштучно, даже если уборка их исходников ранее получила отказ. Число реальных окон определяет macOS, поэтому
автотест количества обращений к ключу не заменяет проверку перехода между двумя сборками на Mac.

Обезличенная диагностика хранилища содержит формат `keychain-file-v1`, число зашифрованных записей, отложенных удалений
старых копий, отметок удаления и признак открытия общего ключа в текущем процессе. Ее чтение не обращается к Связке ключей.
Число отложенных удалений **не означает число неперенесенных секретов**; без чтения старых записей диагностика не доказывает,
что перенос всего прежнего хранилища завершен. Имена записей, адреса подписок, пути и значения секретов в нее не входят.

Старые macOS-сборки до этой миграции не читают новый файл секретов. Автоматического отката приложения на macOS нет;
перед ручной проверкой с последующим возвратом на старую сборку нужна защищенная резервная копия с ключами. Сам ключ
хранилища из Связки ключей не экспортировать. Настройки и открытые метаданные серверов остаются в прежнем формате.

## На компьютере пользователя

Если после проверки нужен возврат на старую сборку, сначала в текущем приложении открыть «Настройки» →
«Резервная копия», включить «Ключи доступа», задать «Пароль для файла» и сохранить зашифрованную копию.
Файл и пароль хранить у себя раздельно; в отчет проверки они не нужны.

1. Установить проверяемую сборку поверх приложения, сохранив прежние данные и Связку ключей. Запускать из «Программы».
2. Открыть список серверов. Проверить, что список и выбранный сервер сохранились. При системном вопросе учесть, что это
   пароль Связки ключей «Вход», а не пароль аккаунта Private Gateway.
3. Один раз нажать «Отказать», когда программа запрашивает секрет для замера или обновления. Окно должно остаться
   открытым; крутилка должна остановиться; сообщение должно предлагать разрешить доступ и повторить действие.
4. Повторить действие и разрешить доступ. Для старых записей первая миграция может запросить дополнительные разрешения.
   После успешной миграции повторить замер и обновление в том же запуске: серии вопросов по каждому серверу быть не должно.
5. Закрыть приложение полностью и открыть снова. Разрешить доступ к одному ключу хранилища, если macOS спрашивает.
   Проверить подключение, замер списка, обновление подписки и сохранение выбранного сервера.
6. Проверить новый импорт и удаление тестового сервера. Не публиковать исходные ссылки, пароли или содержимое Связки ключей
   в отчете. При проблеме достаточно номера сборки, места отказа и обезличенного отчета программы.
7. При первом запросе доступа проверить также «Поделиться», импорт и подключение: отказ должен оставить окно открытым и
   дать понятное сообщение. При отказе доступа к новому серверу действующее подключение, прежний выбор и режим не меняются.
   Повторить действие после разрешения доступа. Если ключ уже открыт в этом процессе, новый системный запрос не требуется.
8. После завершенного переноса установить следующую тестовую сборку поверх приложения. Открыть приложение, разрешить
   доступ к общему ключу при запросе, дважды выполнить замер всего списка и обновление подписок. Отдельных запросов для
   25–30 серверов быть не должно. Повторить еще после одного обновления и после полного завершения процесса.
   Если серия вернулась, нужны версия и коммит **окна приложения**, название элемента в диалоге (`PrivateGateway` либо
   `PrivateGateway.Vault`), действие и наличие повторов в том же процессе; значения секретов и пароль присылать не нужно.

Автотесты: `KeychainFileSecretStoreTests` — количество открытий, отказ и повтор, шифрование, подмена, потеря ключа,
прерывание записи и очистки, 30 старых записей и три следующих запуска при отказе уборки, удаление без возврата старого
входа; `KeychainAccessGateTests` — восстановление режима системных окон и параллельное чтение во время уборки;
`SecretFileTests` — старая копия базы не отменяет удаление; `SubscriptionUpdateTests` — запуск без лишнего чтения и отказ обновления;
`SecretAccessUiTests` — живое окно и повтор команды после отказа; `SecretStoreTests` — настоящее хранилище ОС в CI.
Работа нативных диалогов и правил доступа существующей Связки ключей требует проверки на самом Mac.
