# Проверка прямого внешнего прокси

Настольный клиент, 2026-11-05. Проверки на управляемом стенде и CI не заменяют проверку вашего внешнего сервиса.
Не присылайте в чат или журнал логин, пароль, полный адрес с учетными данными и рабочие ссылки доступа.

1. Сверьте версии окна и службы. Запишите исходный VPN-сервер, DNS, локальный порт и состояние системного прокси.
   В VPN подключитесь как прежде: серверный прокси, если он настроен на VPS, не требует новых полей клиента.
2. В «Настройки» → «Основные» → «Режим» выберите «Только прокси». Введите данные своего сервера в отдельную форму,
   сохраните ее. Внешний порт должен совпадать с данными доступа; локальный порт в «Подключение и ядро» остается прежним.
3. Подключитесь. Проверьте сайт через программу, которая использует локальный или системный прокси. На «Проверке»
   сопоставьте измеренный IP с ожидаемым выходом внешнего сервиса. Это должен быть IP выхода прокси; он не обязан
   совпадать с адресом входного сервера. Обычное приложение без прокси может продолжать видеть прямой IP.
4. Для авторизации по логину/паролю проверьте верные данные и один заведомо неверный пароль. Неверные данные не
   должны давать «Подключено» по одному открытому локальному порту. Верните верный пароль. Для HTTPS сертификат
   проверяется; не отключайте TLS-проверку ради успеха.
5. HTTP/HTTPS проверьте по TCP. UDP от этих вариантов не ожидается. Для SOCKS5 отдельно проверьте UDP-программу,
   только если внешний сервис заявляет UDP ASSOCIATE: рабочий TCP не означает, что UDP поддержан.
6. Проверьте DNS в использующей прокси программе. Запишите выбранный DNS ядра и собственный DoH браузера, не
   меняя их автоматически. Несколько IP одного публичного резолвера не доказывают утечку. Сведения DNS ОС/TUN
   отличаются от внешних рекурсоров браузерного теста. Публичный UDP DNS с HTTP/HTTPS должен давать понятное
   сообщение о выборе DoH, без автоматической подмены или прямого запроса.
7. При обрыве внешнего сервиса соединения через локальный вход не должны незаметно переключаться на прямой выход.
   Системный прокси указывает на локальный порт, пока клиент пытается восстановить связь. При явном отключении
   возвращается его прежняя конфигурация. Общей блокировки остальных программ в режиме прокси нет.
8. Переключитесь в VPN и обратно. VPN-сервер, внешний адрес, авторизация, DNS и локальные параметры сохраняются
   независимо. Выбор VPN-сервера в списке при работающем прокси не меняет его выход; «Подключить VPN» в карточке
   явно выбирает VPN. Смена режима/сохранение формы/отключение во время запуска службы не должны запускать старую цель.
9. Перезапустите программу. Настройки и защищенно сохраненные учетные данные должны восстановиться. Экспортируйте
   диагностический отчет и убедитесь, что логина и пароля в нем нет. Копия без ключей после восстановления требует
   повторного ввода учетных данных; копия с ключами переносит их только внутри зашифрованного файла.

Для разбора достаточно версии окна/службы, протокола, способа авторизации без значений, результата каждого пункта,
времени отказа и обезличенного отчета. Проверка реального публичного IP, UDP и DNS вашего сервиса фиксируется
отдельно от localhost-тестов с настоящим Xray и контролируемыми ответами тестового сайта.
