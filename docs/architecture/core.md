# Ядро: конфиг Xray-core и TUN

Служба не принимает готовый конфиг ядра — только описание сервера и настройки по контракту IPC
(модель угроз). Конфиг Xray собирает `Client.Network/Xray/XrayConfigBuilder` — чистая функция без
сети и файлов, ее проверяют модульные тесты на эталонных ссылках `shared/testdata`.

## Что на входе

`CoreRequest`: сервер (`ServerDefinition` с ключами), режим (VPN или только прокси), «Защита и
утечки», «Подключение и ядро», «Маршрутизация» — то же, что уходит службе в запросе Connect.

## Что в конфиге

- **Вход** — `socks` на порту из «Подключения и ядра» (по умолчанию 10808): к нему подключаются
  программы в режиме прокси и TUN в режиме VPN. Наружу (`0.0.0.0`) — только в режиме прокси и
  только после вопроса «Открыть прокси для локальной сети?»; в режиме VPN вход всегда локальный.
  Определение домена (`sniffing`) — только для правил (`routeOnly`): соединение идет туда, куда
  просили.
- **Выходы** — `proxy` (выбранный сервер), `direct`, `block`; при TLS-фрагментации еще `fragment`,
  через который `proxy` дозванивается (`sockopt.dialerProxy`).
- **Протоколы** — VLESS (с `flow`, например XTLS Vision), VMess, Trojan, Shadowsocks, WireGuard.
  Hysteria2 и TUIC — отказ `UnsupportedProtocol`: их возьмет второе ядро после технического спайка.
  Нет ключей — `MissingCredentials`; транспорт, которого у протокола в Xray нет (QUIC у VLESS), —
  `UnsupportedTransport`.
- **Транспорты** — `raw` (TCP), `ws`, `grpc`, `httpupgrade`, `xhttp` с путем, Host и именем сервиса.
- **Защита** — TLS (SNI, ALPN, отпечаток uTLS, «небезопасный» только если так в ссылке) и REALITY
  (SNI, открытый ключ, short id, spiderX; отпечаток обязателен — из профиля или настройки, иначе
  `chrome`). Отпечаток из «Подключения и ядра» сильнее профиля.
- **Mux** — по настройке, но не с XTLS Vision: они несовместимы.
- **DNS** — DoH Cloudflare или Quad9, свой адрес или по умолчанию DoH Cloudflare; запросы идут через
  туннель. «Только IPv4» — `queryStrategy: UseIPv4` и прямой выход тоже только IPv4.
- **Правила** по порядку: локальная сеть (`geoip:private`) — напрямую, если разрешена, иначе блок;
  IPv6 — блок, если он закрыт; правила для сайтов из «Маршрутизации» в порядке списка
  (`example.com` и `*.example.com` — `domain:example.com`, `geosite:…` как есть, адрес и подсеть —
  условием `ip`); «Напрямую» — только в раздельном режиме. Остальное — через сервер. Для имени Xray
  сначала сверяет правила по имени, а правила по адресу — только если ни одно не подошло
  (`IPIfNonMatch`): правило по имени сильнее правила по адресу и ниже его в списке.
- **Журнал** — уровень из «Подключения и ядра»; журнал соединений и DNS выключен (`access: none`,
  `dnsLog: false`): адреса сайтов в журнал не попадают.

Программы мимо VPN (раздельный режим) — не забота Xray: их отделяет TUN-слой (sing-box) по пути
процесса. Прямой выход самого Xray в режиме VPN (сайты «Напрямую», разрешенная локальная сеть) тоже
уходит через sing-box — см. «Раздельный режим» в [service.md](service.md). В конфиге есть секреты —
ядру он передается через stdin, не файлом и не аргументом командной строки.

## Процесс ядра и прокси-тест

- `Client.Service/Cores/CoreProcess` запускает `xray run -config stdin:` и `sing-box run -c stdin`:
  конфиг с ключами уходит в stdin, а не в файл или аргументы; рабочая папка — папка ядра, у Xray еще
  `XRAY_LOCATION_ASSET` (там `geoip.dat` и `geosite.dat`). Вывод ядра — построчно в событие;
  остановка — с ожиданием выхода, а с отсрочкой (`StopAsync(grace)`) — сначала SIGTERM на macOS и
  Linux, чтобы sing-box успел убрать свои маршруты, и только потом принудительно.
- Сборку ядра кладет `scripts/get-xray.sh` в `artifacts/cores/xray/`: версия — `shared/cores/xray.version`,
  SHA-256 архива сверяется с `.dgst` выпуска и с закрепленной суммой `shared/cores/xray.sha256`
  (Windows x64, macOS arm64, Linux x64; сборка без закрепленной суммы — с предупреждением). В облаке
  агента выпуски GitHub закрыты: `scripts/get-xray.sh --build` собирает ядро из исходников тега через
  go, геобазы берет из ветки `release` Loyalsoldier/v2ray-rules-dat — только для тестов.
- `desktop/tests/Network/XrayProxyTests` — контролируемый прокси-тест на 127.0.0.1: свое ядро-сервер,
  свое ядро-клиент с конфигом от `XrayConfigBuilder` и свой сайт. Протоколы и транспорты: VLESS
  (raw, WebSocket, gRPC, HTTPUpgrade), VMess, Trojan с TLS (самоподписанный сертификат), Shadowsocks
  (aes-256-gcm). Запрос идет через SOCKS5 и через HTTP на одном порту и доходит до сайта; с правилами
  по умолчанию сайт в локальной сети через прокси недоступен. В CI тест идет на Windows, macOS и
  Linux со скачанной сборкой; без сборки тесты с ядром пропускаются.


## TUN режима VPN: sing-box (спайк этапа 3)

Основное ядро и в режиме VPN — Xray: протоколы, правила, DNS и журнал те же, что в режиме прокси.
TUN-адаптера у Xray на десктопе нет, поэтому пакеты в соединения переводит sing-box — отдельным
процессом (GPL-3.0, в код не встраивается) и только этим. Цепочка:

```text
программы → TUN sing-box → SOCKS5 127.0.0.1 (пароль на подключение) → Xray → сервер
```

- `Client.Network/SingBox/SingBoxConfigBuilder.BuildTun` — чистая функция, как и конфиг Xray: вход
  `tun` (172.19.0.1/30, IPv6-адрес — только если IPv6 не закрыт; `auto_route`, строгие маршруты и
  стек из «Подключения и ядра», MTU), один выход — `socks` к Xray, своих правил и DNS нет.
  Адаптер называется `pgtun0` на Linux и `Private Gateway` на Windows — по имени его узнают правила
  блока при обрыве; на macOS имя дает система (`utun…`).
- **Вход Xray только для своего TUN** — `XrayConfigBuilder.Build(request, TunLink)`: SOCKS5 на
  127.0.0.1, случайный порт, имя и пароль — 128 случайных бит на каждое подключение. Другие
  программы машины в обход TUN им не воспользуются; в конфиги они уходят через stdin.
- **Сервер — мимо туннеля.** Служба разрешает имя сервера заранее; Xray соединяется с этим адресом
  (в `vnext`/`servers`, у WireGuard — в `endpoint`; имя для TLS и заголовков прежнее), а адреса
  сервера идут в `route_exclude_address` TUN. Иначе соединение с сервером ушло бы в сам туннель.
  Разрешенная локальная сеть — тоже в исключениях; запрещенная закрыта правилом Xray и в VPN.
- **DNS** — такой же трафик TUN: запрос к любому адресу уходит в Xray, и первое правило Xray (порт 53
  с входа TUN) отдает его выходу `dns`, который отвечает по настройкам DNS этого же конфига — DoH
  Cloudflare, Quad9, свой адрес. Один DNS в режимах прокси и VPN; запрос к роутеру тоже отвечает Xray.
  Собственные запросы DNS Xray идут через сервер — правило только для входа TUN, петли нет. Запрос к
  разрешенной локальной сети мимо TUN закрывает блок при обрыве ([kill-switch.md](kill-switch.md)).
- `Client.Service/Cores/VpnTunnel` поднимает Xray, ждет его порт, поднимает sing-box и ждет адаптер;
  не поднялось за отведенное время или ядро вышло — `TunnelException`, все запущенное остановлено.
  Остановка — наоборот: sing-box с отсрочкой 5 с (снимает маршруты), потом Xray. Ядро вышло само —
  событие `Exited`.
- Сборку кладет `scripts/get-singbox.sh` в `artifacts/cores/sing-box/` вместе с `LICENSE`: версия —
  `shared/cores/sing-box.version`, архив берется только с закрепленной суммой из
  `shared/cores/sing-box.sha256` (Windows x64, macOS arm64, Linux x64). На Windows Wintun встроен в
  сборку sing-box — отдельный драйвер не ставится. Служба ищет sing-box рядом с собой или в
  `artifacts/cores/sing-box`, `--sing-box <путь>` — для разработки; версию отдает `GetServiceInfo`.
- Тест `desktop/tests/Network/VpnTunnelTests` — на Linux под root в своем сетевом пространстве
  (`netns` sing-box, `unshare`/`nsenter`): запрос из пространства на публичный адрес проходит TUN,
  Xray и свой сервер Xray и приходит на свой сайт, DNS-запрос к любому адресу отвечает Xray через
  сервер и DNS теста (выходы сервера теста перенаправлены на них — из машины ничего не уходит); адрес
  машины в локальной сети закрыт; после остановки пути нет, правила маршрутизации sing-box убраны;
  Xray, который умер при запуске, туннеля не дает. Сеть машины тест не трогает. Строгим маршрутам
  нужен IPv6 в ядре ОС — где его нет, тест идет без них. На Windows и macOS, без root, без сборок
  или без `ip`, `curl`, `python3` тест пропускается.

Чего спайк еще не делает: служба в режиме VPN по-прежнему отвечает `VpnNotReady` — туннель включится
в подключение вместе с блоком при обрыве (WFP, nftables), закрытием DNS и IPv6 мимо туннеля и
установкой службы. Раздельный режим (программы мимо VPN) — правила sing-box по процессу ([service.md](service.md)).

## Проверка задержки

- Задержку меряет служба (в интерфейсе сеть запрещена) и меряет через ядро, а не пингом адреса:
  `XrayConfigBuilder.BuildProbe` собирает одно ядро на все серверы — у каждого свой вход SOCKS5 на
  127.0.0.1 и свой выход, вход ведет только в свой выход; настройки подключения (фрагментация, Mux,
  отпечаток) те же, что при подключении. Без DNS, правил и журнала соединений.
- `Client.Service/Cores/LatencyProbe` запрашивает через вход каждого сервера проверочный адрес
  `https://cp.cloudflare.com/generate_204` (пустой ответ, без cookies), по 8 серверов сразу.
  Задержка — время запроса вместе с установкой соединения через сервер: так ее почувствует
  пользователь. Любой ответ адреса — сервер доступен.
- Нет задержки — есть причина (`LatencyFailure`): `Unsupported` — ядро за сервер не возьмется
  (Hysteria2 и TUIC до второго ядра), `NoResponse` — нет ответа за отведенное время, `CoreFailed` —
  ядро не запустилось, проверка не состоялась. Сервер, который отверг ключ, — `NoResponse` сразу;
  недоступный адрес Xray пробует несколько раз, и такой сервер ждет до конца таймаута.
- Контракт: `MeasureLatency` получает `LatencyTarget.server` (сервер целиком) и отвечает
  `LatencyResult` с причиной `failure`; перевод — `ContractMapping`. Интерфейс подключится к
  проверке вместе со службой и IPC (этап 3); до тех пор в списке — значения демо-режима.
- Тесты: `desktop/tests/Network/LatencyProbeTests` — живой, мертвый, неподдерживаемый сервер и сервер
  с чужим ключом на 127.0.0.1, свой сайт вместо проверочного адреса; ядро, которое не запустилось.
