# Блок при обрыве

Блок при обрыве (kill switch) — правила брандмауэра ОС, которые закрывают все, кроме туннеля и
соединения с сервером. Ставит и снимает их только служба. Правила живут в ОС, а не в процессе
службы: упала служба или ядро — блок остается (fail-closed), снимает его только явное отключение.

## Что пропускает (`KillSwitchPolicy`, Core)

Одна политика для всех ОС, исполняет ее `IKillSwitch` своей ОС:

| Что | Почему открыто |
| --- | --- |
| Петля (loopback) | Xray и sing-box говорят друг с другом через 127.0.0.1 |
| Адаптер туннеля (`pgtun0`, `Private Gateway`) | весь трафик в туннель; правило действует и до появления адаптера |
| Сервер — адрес и порт, TCP и UDP | соединение ядра с сервером идет мимо туннеля; адрес служба разрешает до запуска (решение 176) |
| DHCP (IPv4 и IPv6), обнаружение соседей IPv6 | без них машина теряет адрес и сеть; данных наружу через них нет |
| Локальная сеть — только если разрешена | частные сети IPv4 и IPv6 |
| Обнаружение устройств — только вместе с локальной сетью | групповые адреса (mDNS, SSDP) |
| Выход `direct` sing-box — только когда он есть (`DirectExit`) | раздельный режим и прямой выход Xray: программы и сайты, которые пользователь сам отправил мимо VPN, и локальная сеть, если разрешена ([service.md](service.md)) |

DNS мимо туннеля (порты 53 и 853) закрыт раньше локальной сети: при «Блокировать DNS провайдера»
запрос к роутеру не уйдет, даже если локальная сеть разрешена. Выход `direct` — раньше закрытия DNS:
обходу DNS тоже нужен. Все остальное — закрыто.

Служебные исключения на этом и заканчиваются: ни проверки обновлений, ни телеметрии, ни «своих»
адресов мимо туннеля нет. Загрузка подписок идет через туннель (решение по умолчанию «только через VPN»).

## Когда стоит

- Ставит служба при подключении в режиме VPN — **до** запуска ядер; смена сервера заменяет правила
  без щели. Блок выключен в настройках — правил нет.
- Держится, пока защита включена: при сбое ядра (`Error`), после остановки службы и после ее
  падения. Следующий запуск службы видит оставшиеся правила и показывает `Blocked`.
- Перезагрузку переживает только с «Защитой при загрузке» («Защита и утечки», по умолчанию включена):
  на Windows фильтры постоянные — служба фильтрации ставит их при загрузке, еще до старта нашей службы;
  на Linux таблица nftables живет в памяти ядра, поэтому служба запоминает политику и при запуске (раньше
  сети) ставит блок сама. Без нее блок уходит с перезагрузкой ([service.md](service.md), «Аварии и
  перезагрузка»).
- Снимают его отключение, отказ в подключении (защиты нет — так и показано) и переход в режим
  прокси. В строгом режиме («Защита и утечки») ручное отключение блок не снимает: ядра
  останавливаются, блок остается без туннеля — «Блокировка» строгого режима, пока пользователь не
  подключится или не выключит строгий режим ([service.md](service.md)).
- Нет блока для этой ОС (сейчас macOS) — режима VPN нет (`PGC-SVC-006`): VPN без блока не обещается.

## Linux — nftables (`NftablesKillSwitch`, Platform.Linux)

- Своя таблица `inet private_gateway` с цепочками `output` (трафик самой машины) и `forward`
  (контейнеры и виртуальные машины со своим NAT: Docker, libvirt, LXC), обе — priority 0, политика
  drop. Чужие правила (ufw, firewalld, docker) не трогаются, таблица снимается целиком. Блок только сужает: наш drop
  чужим accept не отменить, наш accept не отменяет чужой drop.
- Замена правил — одной транзакцией `nft -f -` (объявить таблицу → удалить → поставить новую): щели
  между старыми и новыми правилами нет. Снятие — то же объявление и удаление: таблицы нет — не ошибка.
- nft вызывается по полному пути (`/usr/sbin/nft`, `/sbin/nft`, `/usr/bin/nft`), без поиска в PATH:
  служба работает от root. Имя адаптера проверяется (буквы, цифры, `_`, `.`, `-`, не длиннее 15
  знаков) — в текст правил ничего чужого не попадет.
- Пересылка (`forward`): в туннель и из него (ответы sing-box контейнерам); DNS мимо туннеля закрыт и
  локальная сеть открыта по тем же настройкам — по адресу назначения, поэтому и запрос контейнера в
  локальную сеть, и ответ ему (адрес контейнера частный) проходят, а наружу мимо туннеля — нет.
  Сервера в пересылке нет: к нему мимо туннеля ходит только сама служба. Тест — «контейнер» в соседнем
  сетевом пространстве за пространством-машиной с NAT.
- Выход `direct` sing-box узнается по метке пакетов: `meta mark 0x5047 accept` (метку ставит
  `routing_mark` в конфиге sing-box). Другие программы с этой меткой не ходят.
- Отброшенный исходящий пакет программа получает как ошибку сразу (EPERM), а не по тайм-ауту.

## Windows — WFP (`WfpKillSwitch`, `WfpRules`, Platform.Windows)

- Свой провайдер и подслой (вес 0xFFFF) Windows Filtering Platform. Фильтры — на слоях установки
  соединения ALE connect и accept, IPv4 и IPv6. Решает подошедший фильтр с наибольшим весом:
  разрешения — 15, закрытие DNS мимо туннеля — 10, локальная сеть — 5, «закрыть все» — 0. Как и на
  Linux, блок только сужает: чужой permit (брандмауэр Windows) наш block не отменяет.
- Политика переводится в фильтры чистой функцией `WfpRules.For` — ее тесты идут на всех ОС.
- Сессия не динамическая: фильтры переживают службу (fail-closed) и уходят при снятии; с «Защитой при
  загрузке» они постоянные (`FWPM_FILTER_FLAG_PERSISTENT`) и переживают перезагрузку, без нее — уходят.
  Провайдер и подслой — постоянные всегда (на них ссылаются постоянные фильтры) и снимаются вместе с
  блоком. Замена — в одной транзакции: прежние фильтры удаляются, новые ставятся.
- Ключи фильтров — по порядку от своего базового GUID (`WfpRules.FilterKey`): после падения службы
  их можно найти и снять без перечисления всех фильтров машины.
- Адаптер туннеля WFP узнает по LUID, а его нет, пока sing-box не поднял TUN. Поэтому служба ставит
  блок до запуска ядер (мимо — только сервер) и еще раз, когда адаптер появился. На Linux повтор
  ничего не меняет.
- Выход `direct` — разрешение с весом 15 по программе sing-box (условие ALE_APP_ID, путь из папки
  службы): его соединения проходят, и DNS тоже.
- Тест в CI идет на машине GitHub с правами администратора, но фильтры там касаются одной программы
  (`curl.exe`, условие ALE_APP_ID): машина CI остается в сети. Служба ставит их на всю машину.

## Тесты

`desktop/tests/Network/VpnModeTests` — блок в подключении службы: с подделкой — блок до ядер и его
политика, блок при сбое ядра, снятие при отключении, отказе и в режиме прокси, оставшийся блок при
запуске — `Blocked`, блок, который не поставился, — честная «Ошибка». Весь путь — в своем сетевом
пространстве с настоящими nftables, sing-box и Xray: «Защищено» за блоком, сбой ядра оставляет
трафик заблокированным, остановка службы — тоже, новый запуск — `Blocked`, отключение все открывает.

`desktop/tests/Network/WfpKillSwitchTests` — правила WFP точным списком на всех ОС; на Windows с
правами (CI) — настоящие фильтры для `curl.exe` и настоящий внешний сервер (github.com по адресу):
открыт только порт сервера (другой порт того же адреса закрыт), петля и адаптер «туннеля»; без
сервера в правилах закрыто все; после снятия все открыто. Локальную сеть и DNS роутера проверяет
только список правил: другой машины в частной сети у машины CI нет, а соединение со своим адресом
Windows считает петлей. Программа выхода `direct` (в тесте — сам curl) проходит куда угодно.

Ядра в тестах режима VPN работают в своем сетевом пространстве Linux (`nsenter`), как на машине:
Xray, sing-box и TUN — в одной сети, сервер теста — на адресе машины по паре veth. Раздельный режим:
программа из списка (curl) идет напрямую даже в закрытую локальную сеть, другая (python3) — через
туннель; прямой выход Xray к адресу документации уходит через sing-box, а не по кругу; метка выхода
`direct` проходит блок nftables, без метки и с чужой меткой — нет.

`desktop/tests/Network/KillSwitchTests`:

- текст правил — точный список на все случаи политики, отказ странным именам адаптера и портам;
- работа с nft — подделкой: что уходит в `nft -f -` и как читается список таблиц;
- настоящие правила — в своем сетевом пространстве Linux (root): две пары veth к сети машины, обычная
  сеть и «туннель». С блоком открыт только порт сервера и адаптер туннеля; разрешенная локальная сеть
  открывается, а DNS роутера остается закрыт до «Блокировать DNS провайдера» = выкл; повторное
  включение заменяет правила; после снятия все открыто. Правила машины тест не трогает. Без root, nft,
  ip, curl или python3 тест пропускается.
