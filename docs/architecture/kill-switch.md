# Блок при обрыве

Блок при обрыве (kill switch) — правила брандмауэра ОС, которые закрывают все, кроме туннеля и
соединения с сервером. Ставит и снимает их только служба. Правила живут в ОС, а не в процессе
службы: упала служба или ядро — блок остается (fail-closed), снимает его только явное отключение.

## Что пропускает (`KillSwitchPolicy`, Core)

Одна политика для всех ОС, исполняет ее `IKillSwitch` своей ОС:

| Что | Почему открыто |
| --- | --- |
| Петля (loopback) | Xray и sing-box говорят друг с другом через 127.0.0.1 |
| Адаптер туннеля (`pgtun0`, `Private Gateway`) | весь трафик в туннель; правило действует и до появления адаптера |
| Сервер — адрес и порт, TCP и UDP | соединение ядра с сервером идет мимо туннеля; адрес служба разрешает до запуска (решение 176) |
| DHCP (IPv4 и IPv6), обнаружение соседей IPv6 | без них машина теряет адрес и сеть; данных наружу через них нет |
| Локальная сеть — только если разрешена | частные сети IPv4 и IPv6 |
| Обнаружение устройств — только вместе с локальной сетью | групповые адреса (mDNS, SSDP) |
| Свой DNS в частной сети — только DNS (53, TCP и UDP) и только к нему (`LanDns`) | «DNS» — свой адрес в локальной сети (Pi-hole): его Xray спрашивает напрямую, через сервер его не достать; остальное к этому адресу — по «Разрешить локальную сеть». Перенаправление DNS в туннель (Linux) его не трогает — иначе запрос Xray вернулся бы в Xray по кругу |
| Выход `direct` sing-box — только когда он есть (`DirectExit`) | раздельный режим и прямой выход Xray: программы и сайты, которые пользователь сам отправил мимо VPN, и локальная сеть, если разрешена ([service.md](service.md)) |

Запросы имен мимо туннеля — DNS (53), DoT (853), LLMNR (5355) и NetBIOS (137, 138) — закрыты раньше
локальной сети: при «Блокировать DNS провайдера» запрос к роутеру не уйдет, даже если локальная сеть
разрешена, а имя, не найденное через DNS, Windows и Samba не станут спрашивать у всей сети (в чужом Wi-Fi
его ловит Responder). Цена: устройства сети по имени NetBIOS и LLMNR не находятся — по адресу или по имени
`.local` (mDNS, порт 5353 — у «Обнаружения устройств»); так и сказано в подписи настройки. Выход `direct` — раньше закрытия DNS:
обходу DNS тоже нужен. Все остальное — закрыто.

Служебное исключение одно и только на время: поиск адреса нового сервера по имени под блоком без туннеля
(`ServiceLookup`). Пока служба ищет, блок пропускает только ее (WFP — по программе службы; nftables — по метке сокета
`0x5048`, ее ставит только root) и только к закрепленному адресу DoH (1.1.1.1:443, TCP); потом возвращается прежний
блок, без исключения. Ни проверки обновлений, ни телеметрии, ни «своих» адресов мимо туннеля нет. Загрузка подписок
идет через туннель (решение по умолчанию «только через VPN»).

## Когда стоит

- Ставит служба при подключении в режиме VPN — **до** запуска ядер; смена сервера заменяет правила
  без щели.
- **Блок выключен в настройках** — те же правила «только туннель» все равно стоят, пока туннель поднят
  («Защищено»): DNS и IPv6 мимо туннеля, программы с привязкой к карте (проверка связи NetworkManager, DNS
  systemd-resolved для карты, DoH Windows по адаптеру), LLMNR — закрыты, и «Блокировать DNS провайдера» и
  «Блокировать IPv6 вне туннеля» держатся не одними маршрутами sing-box. Исключение — IPv6: если «Блокировать IPv6
  вне туннеля» выключено, а у сервера IPv6 нет, IPv6 мимо туннеля открыт и правилами (`Ipv6Outside` политики) — как
  выбрал пользователь; при включенном блоке он закрыт всегда. Выключенный блок решает только, что при
  обрыве: правила снимаются в «Переподключении», «Ошибке», при «Работает другой VPN» и остановке службы — сеть
  открыта, как выбрал пользователь; до туннеля их нет. Они не постоянные и в «Защите при загрузке» не
  участвуют; в файле блока отмечены «открытыми» — служба, упавшая с ними, при запуске их снимает, а не
  показывает «Блокировку». Проверка блока на главной — «выключено».
- Держится, пока защита включена: при сбое ядра (`Error`), после остановки службы и после ее
  падения. Следующий запуск службы видит оставшиеся правила и показывает `Blocked`.
- Перезагрузку переживает только с «Защитой при загрузке» («Защита и утечки», по умолчанию включена):
  на Windows фильтры постоянные — служба фильтрации ставит их при загрузке, еще до старта нашей службы;
  на Linux таблица nftables живет в памяти ядра, поэтому служба запоминает политику и при запуске (раньше
  сети) ставит блок сама. Без нее блок уходит с перезагрузкой ([service.md](service.md), «Аварии и
  перезагрузка»).
- Снимают его отключение и переход в режим прокси. Отказ в подключении режима VPN с блоком его не
  снимает — «Блокировка» с кодом, блок без туннеля; отказ без блока и отказ режима прокси — снимает
  (защиты нет — так и показано) ([service.md](service.md), «Режим VPN», п. 5). В строгом режиме («Защита и утечки») ни ручное отключение, ни отказ в подключении блок не
  снимают: ядра останавливаются, блок остается без туннеля — «Блокировка» строгого режима, пока пользователь не
  подключится или не выключит строгий режим ([service.md](service.md)). Пауза для входа в Wi-Fi снимает
  блок на время и возвращает тот же (с той же постоянностью фильтров); какой блок держит служба — в ее
  файле блока, по нему блок возвращается и после перезапуска службы.
- **Сторож блока.** Пока служба держит блок или правила «только туннель», каждые 15 с она проверяет, что они целы
  (`IKillSwitch.IsIntact`): на Linux — таблица на месте, и обе цепочки (исходящий и пересылаемый трафик) закрывают все,
  что правила не пропустили (`policy drop`); на Windows — на месте все фильтры последнего включения, а не только первый.
  Сняла их другая программа (`nft flush ruleset`, перезапуск nftables или брандмауэра, чистка фильтров) — служба ставит
  тот же блок снова одной транзакцией: в журнале `PGC-SVC-008`, не встал — `PGC-SVC-007`. Без сторожа «Блокировка» и
  «Переподключение» шли бы без блока, а трафик — мимо туннеля. На паузе для входа в Wi-Fi блока нет — сторож молчит.
  Окно уязвимости — до такта сторожа: при обрыве туннеля блок и так ставится заново (без разрешения адаптеру).
- Нет блока для этой ОС (сейчас macOS) — режима VPN нет (`PGC-SVC-006`): VPN без блока не обещается.

## Linux — nftables (`NftablesKillSwitch`, Platform.Linux)

- Своя таблица `inet private_gateway` с цепочками `output` (трафик самой машины) и `forward`
  (контейнеры и виртуальные машины со своим NAT: Docker, libvirt, LXC), обе — priority 0, политика
  drop. Чужие правила (ufw, firewalld, docker) не трогаются, таблица снимается целиком. Блок только сужает: наш drop
  чужим accept не отменить, наш accept не отменяет чужой drop.
- Замена правил — одной транзакцией `nft -f -` (объявить таблицу → удалить → поставить новую): щели
  между старыми и новыми правилами нет. Снятие — то же объявление и удаление: таблицы нет — не ошибка.
- nft вызывается по полному пути (`/usr/sbin/nft`, `/sbin/nft`, `/usr/bin/nft`), без поиска в PATH:
  служба работает от root. Имя адаптера проверяется (буквы, цифры, `_`, `.`, `-`, не длиннее 15
  знаков) — в текст правил ничего чужого не попадет.
- Пересылка (`forward`): в туннель и из него (ответы sing-box контейнерам); DNS мимо туннеля закрыт и
  локальная сеть открыта по тем же настройкам — по адресу назначения, поэтому и запрос контейнера в
  локальную сеть, и ответ ему (адрес контейнера частный) проходят, а наружу мимо туннеля — нет.
  Сервера в пересылке нет: к нему мимо туннеля ходит только сама служба. Тест — «контейнер» в соседнем
  сетевом пространстве за пространством-машиной с NAT.
- Выход `direct` sing-box узнается по метке пакетов: `meta mark 0x5047 accept` (метку ставит
  `routing_mark` в конфиге sing-box). Другие программы с этой меткой не ходят.
- **DNS к разрешенной локальной сети** (роутер из resolv.conf там, где нет systemd-resolved): частные сети тогда
  в исключениях TUN, запрос идет мимо туннеля, а там DNS закрыт — имена не разрешались совсем. Пока туннель
  поднят, цепочка `dns` (`type nat hook output priority -100`) перенаправляет такой запрос (порт 53, TCP и UDP,
  к частным адресам, не в адаптер туннеля, без метки выхода sing-box) в адрес DNS туннеля 172.19.0.2 — его
  отвечает Xray. Фильтр после nat видит прежний интерфейс, поэтому запросы к 172.19.0.2:53 разрешены раньше
  закрытия DNS. Перенаправленный запрос сокета с привязкой к карте (SO_BINDTODEVICE) после nat все равно ушел бы в
  карту — к роутеру с адресом 172.19.0.2; цепочка `dns_out` (postrouting) закрывает 172.19.0.2:53 не через адаптер
  туннеля, уже по настоящему интерфейсу. Запрос к своему адресу машины (свой DNS-сервер на адресе в сети) идет через
  петлю — его перенаправление не трогает. Только при «Разрешить локальную сеть» и «Блокировать DNS провайдера»: без
  локальной сети DNS к ней и так идет в туннель, без закрытия DNS роутер разрешен. На Windows ОС спрашивает DNS
  адаптера туннеля.
- Закрытый TCP — отказом (`reject with tcp reset`, последнее правило output и forward, и запросы имен по TCP): программа
  получает «отказано» сразу, а не ждет повторов SYN до двух минут. Отброшенный исходящий UDP программа получает
  ошибкой сразу и так (EPERM).

## Windows — WFP (`WfpKillSwitch`, `WfpRules`, Platform.Windows)

- Свой провайдер и подслой (вес 0xFFFF) Windows Filtering Platform. Фильтры — на слоях установки
  соединения ALE connect и accept, IPv4 и IPv6. Решает подошедший фильтр с наибольшим весом:
  разрешения — 15, закрытие DNS мимо туннеля — 10, локальная сеть — 5, «закрыть все» — 0. Как и на
  Linux, блок только сужает: чужой permit (брандмауэр Windows) наш block не отменяет.
- Политика переводится в фильтры чистой функцией `WfpRules.For` — ее тесты идут на всех ОС.
- Сессия не динамическая: фильтры переживают службу (fail-closed) и уходят при снятии; с «Защитой при
  загрузке» они постоянные (`FWPM_FILTER_FLAG_PERSISTENT`) и переживают перезагрузку, без нее — уходят.
  Провайдер и подслой — постоянные всегда (на них ссылаются постоянные фильтры) и снимаются вместе с
  блоком. Замена — в одной транзакции: прежние фильтры удаляются, новые ставятся.
- Ключи фильтров — по порядку от своего базового GUID (`WfpRules.FilterKey`): после падения службы
  их можно найти и снять без перечисления всех фильтров машины.
- Адаптер туннеля WFP узнает по LUID, а его нет, пока sing-box не поднял TUN. Поэтому служба ставит
  блок до запуска ядер (мимо — только сервер, разрешения адаптеру нет: адаптер прошлого подключения при
  смене сервера может еще не уйти, и с ним не встали бы фильтры пересылки) и еще раз, когда адаптер
  появился.
- Выход `direct` — разрешение с весом 15 по программе sing-box (условие ALE_APP_ID, путь из папки
  службы): его соединения проходят, и DNS тоже.
- **Пересылка** (мобильный хот-спот, общий доступ к интернету, ВМ и контейнеры с NAT) — фильтры на слоях
  IPFORWARD v4 и v6 в том же подслое, только пока адаптера туннеля нет (обрыв, переподключение,
  «Блокировка», «Ошибка», строгий режим, загрузка): пропускаются пакеты самой машины (флаги pass-through —
  их решают слои соединений), локальная сеть по настройке — по адресу назначения в обе стороны, остальное
  закрыто. Портов и программ на слое пересылки нет — ни сервера, ни DNS, ни обхода там нет. Пока туннель
  поднят, фильтров пересылки нет: ее ведут в туннель маршруты sing-box; закрывать пересылку и в «Защищено»
  — после проверки у пользователя (WSL, хот-спот, Hyper-V). **Контейнеры Windows за WinNAT** (Docker с
  изоляцией процессов) слои пересылки не видят: проба в CI 2026-10-25 (nanoserver ltsc2025) — с фильтрами
  пересылки контейнер выходит в сеть. Закрывают ли их фильтры соединений на всю машину (без условия
  программы, как ставит служба) — проверить у пользователя; проба — тест
  `Probe_container_behind_nat_and_the_forward_filters` (`PG_FORWARD_PROBE=1`, нужен docker), в CI не идет.
- **ВМ WSL и Hyper-V** — брандмауэром Hyper-V (Windows 11 22H2 и новее): трафик ВМ через NAT может идти
  мимо слоев IP WFP. Пока туннеля нет, служба ставит два правила «закрыть все» — исходящие и входящие — классом
  WMI `MSFT_NetFirewallHyperVRule` со своими постоянными InstanceID (`HyperVFirewall`); с туннелем и при снятии
  блока снимает. Если оба правила уже стоят, повторная постановка блока их не трогает — снять и поставить заново
  значило бы открыть ВМ на это время. Правила хранятся постоянно: оставшиеся без фильтров WFP (служба упала, перезагрузка без
  «Защиты при загрузке») служба снимает при запуске (`WfpKillSwitch.ForService`). Брандмауэра Hyper-V нет
  (Windows 10, Windows 11 до 22H2) — блок ставится без них, в журнале предупреждение (`IKillSwitch.Warning`,
  одно и то же — один раз). Внешний коммутатор Hyper-V (мост) и Windows Sandbox так не закрываются.
- Машина как DHCP-сервер хот-спота и ВМ (UDP 67 → 68) разрешена всегда, только к частным адресам, 0.0.0.0
  и 255.255.255.255: без этого клиенты не получают адрес и в «Защищено». Так же на Linux (nftables).
- Разрешение адаптеру туннеля — только пока туннель поднят: при обрыве, перед каждой попыткой
  переподключения, при сдаче, после сбоя ядра, при «Работает другой VPN», при остановке службы и в
  строгом режиме служба ставит блок заново без него (`Gateway.BlockWithoutTunnel`) — на Windows так
  включается и закрытие пересылки. Фильтры, оставшиеся после аварии службы с разрешением туннелю, служба при
  запуске заменяет блоком из файла блока — без туннеля, одной транзакцией. Не встал блок без туннеля при
  обрыве — переподключение идет (прежний блок держит трафик машины, каждая попытка ставит его заново); не
  встал и при сдаче — «Ошибка» `PGC-SVC-007`, а не «Блокировка».
- Тест в CI идет на машине GitHub с правами администратора, но фильтры соединений там касаются одной
  программы (`curl.exe`, условие ALE_APP_ID): машина CI остается в сети. Фильтры пересылки программы не
  знают и встают на всю машину — у машины CI пересылки нет. Служба ставит все на всю машину.

## macOS — pf (`PfKillSwitch`, Platform.MacOS)

- Свой якорь `com.apple/250.PrivateGateway`: штатный `/etc/pf.conf` вызывает все якоря `com.apple/*`, поэтому основные
  правила машины не меняются. Правила — `pass out quick …` для петли, туннеля (`utun225` — свой номер адаптера sing-box,
  выше штатных utun0–utun3), сервера (адрес и порт, TCP и UDP), поиска сервера службой (DoH, только сокеты root), своего
  DNS в частной сети, DHCP и соседей IPv6; затем закрытие DNS мимо туннеля (53, 137, 138, 853, 5355; TCP — сбросом),
  IPv6 мимо туннеля и локальная сеть — по политике; в конце `block return out quick proto tcp all` и
  `block drop out quick all`. Правила `out` действуют и на пересылаемое (общий доступ к интернету): его пакеты выходят
  через карту машины.
- Замена правил — одной загрузкой якоря (`pfctl -a … -f -`); снятие — `pfctl -a … -F all`. pf включается своей ссылкой
  (`pfctl -E`, токен в `/var/run/private-gateway/pf.token`) и ею же отпускается (`pfctl -X`): pf, включенный другой
  программой или пользователем, остается включенным.
- Цел (`IsIntact`) — правила якоря на месте, pf включен, а основные правила все еще вызывают `com.apple/*`: свой
  pf.conf без этой строки — и якорь никто не вызывает.
- Обход туннеля в раздельном режиме по программе pf не различает (меток пакетов, как в Linux, у sing-box на macOS нет):
  с блоком при обрыве обход закрыт, и блок говорит это предупреждением (`Warning`).
- Правила pf перезагрузку не переживают: «Защиту при загрузке» служба ставит сама при запуске (launchd запускает ее с
  ОС), как на Linux.

## Тесты

`desktop/tests/Network/VpnModeTests` — блок в подключении службы: с подделкой — блок до ядер и его
политика, блок при сбое ядра, снятие при отключении, отказе и в режиме прокси, оставшийся блок при
запуске — `Blocked`, блок, который не поставился, — честная «Ошибка». Весь путь — в своем сетевом
пространстве с настоящими nftables, sing-box и Xray: «Защищено» за блоком, сбой ядра оставляет
трафик заблокированным, остановка службы — тоже, новый запуск — `Blocked`, отключение все открывает.

`desktop/tests/Network/WfpKillSwitchTests` — правила WFP точным списком на всех ОС; на Windows с
правами (CI) — настоящие фильтры для `curl.exe` и настоящий внешний сервер (github.com по адресу):
открыт только порт сервера (другой порт того же адреса закрыт), петля и адаптер «туннеля»; без
сервера в правилах закрыто все; после снятия все открыто. Локальную сеть и DNS роутера проверяет
только список правил: другой машины в частной сети у машины CI нет, а соединение со своим адресом
Windows считает петлей. Программа выхода `direct` (в тесте — сам curl) проходит куда угодно.

Ядра в тестах режима VPN работают в своем сетевом пространстве Linux (`nsenter`), как на машине:
Xray, sing-box и TUN — в одной сети, сервер теста — на адресе машины по паре veth. Раздельный режим:
программа из списка (curl) идет напрямую даже в закрытую локальную сеть, другая (python3) — через
туннель; прямой выход Xray к адресу документации уходит через sing-box, а не по кругу; метка выхода
`direct` проходит блок nftables, без метки и с чужой меткой — нет.

Покрытие (`VpnModeTests.Coverage`): с блоком и без «провод» пространства (`WireTap` — AF_PACKET на паре к сети
машины, только исходящие, уже после nftables) за время теста видит только соединение Xray с сервером, а через
туннель доходят curl от root и от другого пользователя, разрешитель ОС (DNS ОС — адрес туннеля или роутер), git,
UDP на 443; ICMP и программа с привязкой к карте на провод не выходят. Без python3, git, getent или setpriv тест
пропускается.

Долгий прогон (soak, `VpnModeTests.Soak`, `ReconnectTests.Soak`, `Soak.cs`) — по `PG_SOAK_MINUTES`, иначе пропускается;
ночью — workflow `soak.yml`, вручную — `scripts/soak.sh [минут]`. Сбои идут по кругу, пока не выйдет время: сервер пропал
и вернулся, смена сети, сон, sing-box и Xray убиты (`kill -9`), правила сняла другая программа (`nft flush ruleset`),
пауза для входа в Wi-Fi, отключение и подключение; после каждого — снова «Защищено» и трафик через туннель. Сторож
(`LeakSentinel`) каждые 250 мс шлет из пространства запрос к сайту в локальной сети машины: через туннель он не проходит
никогда, блок его тоже не пропускает — ответ сайта вне разрешенных окон (выключение защиты, пауза, правила, снятые другой
программой, — до возврата блока сторожем) считается утечкой с временем и шагом. В конце — ресурсы процесса службы
(дескрипторы, потоки, управляемая память) и число живых ядер не выросли с первого круга, таблицы nftables и правила
маршрутов пространства те же. Режим прокси — на трех ОС: после каждого сбоя «Защищено» и системный прокси снова на входе
ядра, на паузе и после отключения — прежний.

`desktop/tests/Network/KillSwitchTests`:

- текст правил — точный список на все случаи политики, отказ странным именам адаптера и портам;
- работа с nft — подделкой: что уходит в `nft -f -` и как читается список таблиц;
- настоящие правила — в своем сетевом пространстве Linux (root): две пары veth к сети машины, обычная
  сеть и «туннель». С блоком открыт только порт сервера и адаптер туннеля; разрешенная локальная сеть
  открывается, а DNS роутера остается закрыт до «Блокировать DNS провайдера» = выкл; повторное
  включение заменяет правила; после снятия все открыто. Правила машины тест не трогает. Без root, nft,
  ip, curl или python3 тест пропускается.
