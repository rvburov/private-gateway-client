# Архитектура десктопа

Десктоп — два процесса и готовые ядра. Интерфейс работает с правами пользователя и не трогает
сеть; все, что меняет сеть машины, делает служба с правами администратора. Как они собираются в
выпуск и раскладываются по папкам — [release.md](release.md).

```
┌──────────────────────────────┐   gRPC по named pipe /    ┌───────────────────────────────┐
│ PrivateGateway (интерфейс)   │   Unix-сокету, контракт   │ PrivateGateway.Service        │
│ права пользователя           │ ────────────────────────▶ │ права администратора / root   │
│                              │   shared/specifications/  │                               │
│ Client.UI                    │   ipc/*.proto             │ Client.Service                │
│  └ Client.Application        │                           │  ├ Client.Network (конфиг)    │
│     ├ Client.Network (разбор)│ ◀──────────────────────── │  └ Client.Platform.<ОС>       │
│     └ Client.Contracts       │   состояние, журнал, пинг │      TUN, блок при обрыве, DNS│
│ Client.Infrastructure        │                           │                               │
│  SQLite, секреты ОС, журнал, │                           │  запускает ядра отдельными    │
│  загрузка списков серверов   │                           │  процессами: xray, sing-box   │
└──────────────────────────────┘                           └───────────────────────────────┘
```

## Слои

| Проект | Что внутри | Может ссылаться на | Сеть |
| --- | --- | --- | --- |
| `Client.Core` | модели и правила без ввода-вывода: состояния защиты и переходы, протоколы, маскирование секретов, интерфейсы платформы | — | нет |
| `Client.Contracts` | контракт IPC (код из `.proto`) и перевод перечислений ядра в контракт | Core | — |
| `Client.Network` | разбор ссылок и подписок, сборка конфигов ядер, правила «зашифрован ли трафик» — чистые функции | Core | нет |
| `Client.Application` | сценарии: подключение, смена сервера, импорт, обновление серверов, проверка, правила уведомлений | Core, Contracts, Network | нет |
| `Client.Infrastructure` | SQLite, секреты в хранилище ОС, Serilog, клиент службы по IPC, загрузка списков серверов, уведомления ОС (D-Bus, WinRT) | Core, Contracts, Application | только загрузка списков |
| `Client.UI` | Avalonia: окна, модели представлений, тема из токенов | Core, Contracts, Application, Infrastructure | нет |
| `Client.Service` | служба: сервер IPC, запуск ядер, состояние защиты, пинг, проверки | Core, Contracts, Network, Platform.* | да |
| `Client.Platform.Windows` | Wintun, WFP, служба Windows, определение сети (WLAN API, NLM) | Core | да |
| `Client.Platform.Linux` | nftables, systemd, systemd-resolved, polkit, NetworkManager | Core | да |
| `Client.Platform.MacOS` | служба launchd, pf, маршруты (`netstat`), DNS ОС (`scutil`), системный прокси (`networksetup`), Связка ключей; TUN — sing-box (utun) | Core | да |

Правила держат тесты `desktop/tests/Architecture` (объявленные ссылки в `.csproj` и
используемые сборки) и анализатор запрещенных вызовов (`desktop/BannedSymbols.NoNetwork.txt`).

## Одинаковые контракты на всех ОС

Логика защиты — одна для всех ОС (`Gateway`, `ConnectionStateMachine`); различаются только платформенные части за
интерфейсами `Client.Core.Platform`. Поэтому сценарии проверяются одни, а ОС дает свои части (решение 369):

| Контракт | Что одинаково | Windows | Linux | macOS | Тесты |
| --- | --- | --- | --- | --- | --- |
| Блок при обрыве (`IKillSwitch`) | ставится и меняется без щели, отказ в новой политике оставляет прежний блок, снимается и повторно | WFP | nftables | pf | `PlatformContractTests` (настоящие правила: WFP для одной программы, nftables в своем пространстве, pf в своем якоре); трафик — `WfpKillSwitchTests`, `KillSwitchTests`, загрузка — `PfKillSwitchTests` |
| Хранилище секретов службы (`ISecretSealer`) | шифр не содержит секрета, каждый раз разный, испорченное и чужое не открывается | DPAPI | systemd-creds | Связка ключей | `PlatformContractTests`, `BootConnectionTests` |
| Маршруты, чужой VPN (`IRouteTable`) | маршрут ко всему интернету через карту виден, имена адаптеров чистые | IP Helper | `ip` | `netstat` | `PlatformContractTests`, `RouteTableTests` |
| Сон и пробуждение (`ISuspendClock`) | без сна часы сна стоят, сон — не меньше нуля; пробуждение — проверка сервера сразу | счетчики прерываний | `CLOCK_BOOTTIME` | `mach_continuous_time` | `PlatformContractTests`; `ReconnectTests.Waking_up_checks_the_server_at_once` |
| Ручной выход и переподключение | только к выбранному серверу, смена сети — попытка сразу, политика «Не повторять» | общая логика | общая логика | общая логика | `ReconnectTests` — с настоящим Xray на всех трех ОС |
| DNS и IPv6 | DNS ОС — в туннель, IPv6 вне туннеля закрыт или через туннель, замер утечек честный | sing-box (DNS адаптера), WFP | sing-box (resolved), nftables | служба (`scutil`), pf | `LeakCheckTests` на всех ОС; путь трафика — `VpnModeTests` и `VpnTunnelTests` в пространствах Linux, DNS macOS — `ScutilDnsTests` |

На машинах CI правила ставятся так, чтобы не отрезать саму машину; полный путь трафика через TUN и блок при обрыве
проверяется в сетевых пространствах Linux. На настоящих Windows и macOS с туннелем — проверка вручную (README, этап 11).

## Ход подключения

1. Пользователь добавляет профиль: ссылка, QR, файл или адрес подписки. `Client.Network`
   разбирает текст в модели ядра, `Client.Infrastructure` сохраняет профиль в SQLite, ключи — в
   хранилище ОС.
2. Кнопка-щит: `Client.Application` собирает `ConnectRequest` — описание сервера и настройки
   защиты — и отправляет службе.
3. Служба проверяет запрос (UNSPECIFIED и неизвестные значения — отказ), собирает конфиг ядра
   сама, включает блок при обрыве **до** запуска ядра ([kill-switch.md](kill-switch.md)), поднимает
   TUN, запускает ядро.
4. Служба меряет внешний IP, проверяет DNS и IPv6 и шлет `Status` в поток `WatchStatus`. Главный
   экран, трей и уведомления показывают одно и то же состояние.

## Состояния защиты

`Off → Connecting → Connected`; из `Connected` — `Reconnecting` (обрыв), `Connecting` (смена
сервера), `Error`, `Off`. `Reconnecting → Connected | Blocked | Error | Off`. `Blocked` и `Error`
восстанавливаются только через `Connecting`. Выключить можно из любого состояния. Трафик идет
мимо туннеля только в `Off`. Таблица переходов — `ConnectionStateMachine`, тесты — `Unit`.

## Связь интерфейса и службы

- gRPC по локальному каналу: named pipe на Windows, Unix-сокет на Linux и macOS. В сеть служба
  не слушает.
- Доступ к каналу — только у пользователя, установившего службу, и у администраторов: на Unix
  uid собеседника проверяется у ядра ОС, на Windows — список доступа pipe; подробно —
  [service.md](service.md), коды ошибок — [errors.md](errors.md).
- Служба не принимает готовый конфиг ядра, пути к файлам и команды — только описание сервера и
  настройки. Конфиг с путями для логов, записанный от имени администратора, был бы способом
  повысить права.
- Контракт версионируется пакетом (`privategateway.ipc.v1`); интерфейс первым вызывает
  `GetServiceInfo` и сверяет версию.
- Перевод в контракт и обратно — `ContractMapping`: перечисления, сервер с ключами
  (`ServerEndpoint`), настройки защиты, подключения и маршрутизации, состояние (`Status`). Перевод
  туда и обратно дает то же самое — тест на всех эталонах ссылок; UNSPECIFIED, сервер без данных
  своего протокола и порт вне 1–65535 — ошибка отправителя, а не догадка.

## Хранение

| Что | Где |
| --- | --- |
| Профили, подписки, настройки | SQLite в папке данных пользователя |
| Ключи, пароли, UUID, адреса подписок | хранилище ОС (`ISecretStore`): Windows — DPAPI текущего пользователя, зашифрованное значение в своем файле `secrets.db` рядом с базой каталога (не в `app.db`: каталог пишет секрет посреди своей транзакции, решение 487); macOS — Связка ключей (служба «PrivateGateway»); Linux — Secret Service через libsecret. Нет хранилища — секреты не сохраняются вовсе |
| Журнал интерфейса | файл в папке данных пользователя, через `SecretMasker` |
| Журнал службы | в памяти (500 записей) и на диске — `journal.jsonl` в папке состояния службы (1 МБ, плюс прежний `journal.1.jsonl`, права только у владельца), через `SecretMasker`; интерфейс читает через `WatchLog`, после аварии — и записи до нее |
| Ядра | `runtimes/` при разработке (скачиваются скриптом), каталог установки — в выпуске |
