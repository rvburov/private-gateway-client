# Сборка выпуска

Как из исходников получается то, что ставится пользователю, и как программа узнает о новой версии. Подпись кода
(Authenticode, Apple) — «Отложено» (README); обновление программы проверяется своей подписью манифеста (ниже).

## Что в выпуске

`scripts/publish.sh [версия]` на машине нужной ОС (в CI — workflow `publish.yml`, три ОС) собирает выпуск
`PrivateGateway-<версия>-<rid>` (`win-x64`, `linux-x64`, `osx-arm64`):

```
PrivateGateway-<версия>-<rid>/
  PrivateGateway(.exe)            окно
  PrivateGateway.Service(.exe)    служба — рядом с окном: окно ищет ее в своей папке (UserServiceLauncher)
  *.dll, *.so, *.dylib            .NET и пакеты — самодостаточная сборка, ставить .NET не нужно
  cores/xray/                     Xray-core и geosite.dat — служба ищет ядро в cores/ рядом с собой
  cores/sing-box/                 sing-box (TUN режима VPN, GPL-3.0, отдельный процесс) и его LICENSE
  sbom.cdx.json                   SBOM этого выпуска
  THIRD-PARTY-NOTICES.txt         открытые компоненты, их авторство и полные тексты лицензий
```

- Окно и служба — `dotnet publish -r <rid> --self-contained` с ReadyToRun (быстрее запуск — окно стартует с системой).
  Отладочные символы и XML-документация своих сборок в выпуск не идут. Версия — `-p:Version`, по умолчанию `<Version>`
  из `Directory.Build.props`; не SemVer — отказ.
- Ядра качаются заново при каждой сборке выпуска: `scripts/get-xray.sh --pinned` и `scripts/get-singbox.sh` берут
  только архивы с суммой, закрепленной в `shared/cores/*.sha256`. Сборка Xray из исходников (`--build`, облако) и что
  угодно, лежащее в `artifacts/cores`, в выпуск не попадают.

## SBOM и контрольные суммы

`scripts/package.cs` (вызывает `publish.sh`) пишет в `artifacts/release/`:

- `<имя>.zip` (Windows) или `<имя>.tar.gz` (Linux, macOS — права на запуск сохраняются); пакеты ОС — ниже;
- `<имя>.cdx.json` — SBOM в формате CycloneDX 1.6, он же в архиве как `sbom.cdx.json`:
  - пакеты NuGet обоих приложений — из их `*.deps.json`, с SHA-512 пакета и лицензией из `.nuspec` в кеше пакетов;
  - среда .NET и ASP.NET Core (runtime pack);
  - Xray-core (MPL-2.0) и sing-box (GPL-3.0-or-later) — версия из `shared/cores/*.version`, SHA-256 файла;
  - геобаза сайтов `geosite.dat` (MIT) — своя сборка из v2fly/domain-list-community закрепленного коммита
    (`shared/cores/geosite.version`, `scripts/get-geosite.sh`: генератор того же репозитория, go в CI), версия — коммит,
    SHA-256 файла; геобаза из архива Xray (Loyalsoldier, GPL-3.0) остается для тестов. `geoip.dat` выпуск не возит: локальные сети
    служба пишет в конфиг списком (`XrayConfigBuilder.LocalNetworks`), а GeoIP в нем — данные MaxMind GeoLite2;
  - время — `SOURCE_DATE_EPOCH` (время коммита), чтобы две сборки одного коммита не расходились во времени.

  Лицензии ядер и геобаз — из `shared/licenses/components.json` (ниже). Неполный SBOM не пишется: пакет без лицензии
  в `.nuspec`, ядро без версии или файла — ошибка сборки.
- `SHA256SUMS` — суммы всех файлов папки выпуска, проверяются `sha256sum -c SHA256SUMS`.

## Пакеты Linux

`scripts/package-linux.sh <версия>` (шаг `publish.yml` на Ubuntu) собирает из папки сборки `.deb` и `.rpm` — nfpm по
`desktop/packaging/linux/nfpm.yaml` (CI ставит nfpm v2.47.0 через `go install`: модуль сверяется по sum.golang.org):

- `/opt/private-gateway/` — папка сборки целиком (окно, служба, ядра, SBOM, THIRD-PARTY-NOTICES);
- `/usr/share/applications/private-gateway.desktop` — запись меню (RU и EN), `/usr/share/icons/hicolor/scalable/apps/
  private-gateway.svg` — значок, `/usr/bin/private-gateway` — команда окна;
- зависимости — то, без чего не запустится самодостаточная сборка: ICU, fontconfig, X11 (libX11, libICE, libSM);
  nftables — рекомендуется (блок при обрыве).

Службу пакет не ставит: при установке пакета неизвестно, чей это компьютер (`--owner`), поэтому ее ставит окно —
«Установить службу» (pkexec), как и без пакета. Удаление пакета (`remove`, `purge`, у rpm — последняя копия) сначала
удаляет службу (`--uninstall`: юнит systemd, таблица блока при обрыве, папка службы и ее состояние в
`/var/lib/private-gateway`) — машина не остается без сети.
Обновление пакета (`postinstall`, служба уже стоит) переустанавливает службу из новой версии для того же владельца —
он берется из юнита (`--owner`), — иначе работала бы старая копия службы рядом с новым окном; не вышло — строка в
выводе пакетного менеджера, а окно покажет несовпадение версий и «Обновить службу». Данные пользователя
(`~/.local/share/private-gateway`) остаются.

`scripts/tests/linux-package-smoke.sh` (шаг `publish.yml`) на машине CI ставит `.deb` через apt со всеми
зависимостями, сверяет файлы, команду, версию службы и запись меню (`desktop-file-validate`), ставит службу так же, как
окно, ждет ее под systemd (копия без файлов окна, состояние в `/var/lib/private-gateway` с правами 0700), ставит
службу из копии, которая не запускается (нет библиотеки gRPC), — установка отвечает ошибкой, а прежняя служба снова
работает, — ставит пакет поверх (служба перезапущена из новых файлов, владелец тот же), удаляет пакет и проверяет, что
не осталось службы, юнита, таблицы блока, состояния, файлов пакета, а данные пользователя на месте.

## Установщик Windows

`scripts/package-windows.sh <версия>` (шаг `publish.yml` на Windows) собирает `PrivateGateway-<версия>-win-x64.msi` —
WiX 5.0.2 (MS-RL; с v6 у WiX отдельный сбор Open Source Maintenance Fee) по `desktop/packaging/windows/Product.wxs`:

- программа — в `Program Files\Private Gateway` на всю машину, ярлык в меню «Пуск» с AUMID окна (уведомления
  приходят от имени программы), значок и ссылка в «Установленных приложениях»; версия MSI — цифры SemVer;
- служба — той же командой, что из окна: `PrivateGateway.Service.exe --install --owner [OWNER]` (свойство `OWNER` — SID
  владельца, по умолчанию тот, кто ставит), копия в `Program Files\Private Gateway\Service`, состояние в
  `ServiceState`, запуск с Windows; не встала — установка откатывается (откат первой установки удаляет службу);
- обновление (MajorUpgrade) службу не удаляет: `--install` новой версии заменяет ее атомарно (docs/architecture/
  service.md, «Установка») — не запустилась новая, работает прежняя, а MSI откатывается к прежней версии программы;
- понижение версии разрешено (`AllowDowngrades`): MSI прежней версии ставится поверх новой тем же путем — так работает
  откат на прежнюю версию из «О программе»;
- удаление (не обновление) сначала удаляет службу: `--uninstall` снимает блок при обрыве и удаляет папки службы и
  ее состояния;
- файлы пользователя (`%LOCALAPPDATA%\PrivateGateway`) и чужие файлы в папке программы установщик не трогает.

`scripts/tests/windows-installer-smoke.sh` (шаг `publish.yml`) на машине CI ставит MSI тихо (`msiexec /i /qn`),
сверяет файлы, ярлык, запись в «Установленных приложениях», версию и работу службы и ее команду (папка службы,
владелец, папка состояния), что служба без файлов окна и пишет журнал в `ServiceState`. Потом — обновление: та же
сборка в MSI с версией на единицу выше (`package-windows.sh <версия> <версия MSI>`) ставится поверх, служба работает,
ее состояние на месте; неудачное обновление (`OWNER=1000` — не SID, служба не ставится) откатывается к прежней версии с
работающей службой того же владельца; копия службы без библиотеки gRPC сменяется прежней; MSI прежней версии ставится
поверх новой (откат) — служба того же владельца работает, ее состояние на месте. В конце удаляет (`msiexec /x /qn`) и проверяет, что не осталось службы, ее папок, окна и ярлыка, а чужой файл в папке программы и
данные пользователя на месте.

## Программа macOS

`scripts/package-macos.sh <версия>` (шаг `publish.yml` на macOS) собирает из папки сборки `Private Gateway.app` и кладет
его в образ диска `PrivateGateway-<версия>-osx-arm64.dmg` (HFS+, сжатый) рядом с ярлыком на «Программы» (решение 367):

- `Contents/MacOS/` — папка сборки целиком: окно (`CFBundleExecutable` — `PrivateGateway`), служба рядом с ним, ядра в
  `cores/`, SBOM и THIRD-PARTY-NOTICES; `Contents/Resources/PrivateGateway.icns` — значок (`scripts/gen-icons.cs`);
  `Info.plist` — идентификатор `io.github.rvburov.private-gateway` (как метка службы launchd), версия без суффикса
  предварительного выпуска, macOS 14 и новее;
- подпись — ad-hoc, без сертификата: сначала каждый файл `Contents/MacOS`, кроме главного исполняемого (codesign
  считает их вложенным кодом; у сборок .NET и данных подпись ложится в расширенные атрибуты), потом пакет целиком; `codesign --verify --deep --strict`
  проверяет ее при сборке. На Apple Silicon
  код без подписи не запускается вовсе, а подпись пакета — печать его целостности. Подпись Developer ID и нотаризация —
  «Отложено»: до них macOS при первом запуске загруженной программы просит открыть ее вручную («Системные настройки» →
  «Конфиденциальность и безопасность» → «Все равно открыть»), так и сказано в заметках к выпуску.

Службу образ не ставит — ее ставит окно («Установить службу», пароль администратора), из пакета, как и без него.
`scripts/tests/macos-package-smoke.sh` (CI, одноразовая машина) монтирует образ, сверяет подпись, Info.plist и состав,
ставит службу из пакета от root с владельцем — пользователем, проверяет launchd, сокет IPC и права папки состояния,
удаляет службу и сверяет, что подпись пакета после этого цела (служба в пакет не пишет).

## Выпуски на GitHub и поэтапная раскатка

Выпуск — тег `v<SemVer>` на коммите `master`: `git tag v1.2.3 && git push origin v1.2.3`. `release.yml` вызывает
`publish.yml` (сборки трех ОС со всеми проверками и установкой пакетов), затем `scripts/release.cs assemble`:

- каждый файл сборки сверяется со своим `SHA256SUMS` (порча при передаче между заданиями — ошибка), без MSI, `.deb`
  или образа диска macOS выпуск не собирается;
- в выпуск — файлы ОС, общий `SHA256SUMS` и `update.json` — манифест обновления:

  ```json
  { "version": "1.2.3", "channel": "stable", "rollout": 20, "published": "…", "notes": "https://github.com/…/v1.2.3",
    "highlights": [ "…" ],
    "assets": { "win-x64-msi": { "file": "…", "sha256": "…", "size": 0 }, "linux-x64-deb": { … }, "osx-arm64-dmg": { … } } }
  ```

- `update.json.sig` — подпись манифеста (раздел «Подпись обновлений»), тоже в `SHA256SUMS`;
- главное для карточки обновления в окне (`highlights`) — до трех строк: сначала «Новое», потом «Исправлено»;
- заметки — из коммитов с прошлого тега по видам (`feat` — «Новое», `fix` — «Исправлено», `ci`/`test`/`docs`… —
  «Сборка, проверки, документация») и как сверить загрузку.

Версия с «-» (`1.3.0-beta.1`) — бета: выпуск помечен prerelease, канал `beta` (его получают те, у кого в «О программе»
выбран канал «Бета»), раскатка 100 %. Стабильный выпуск раскатывается поэтапно: сначала 20 %, дальше — кнопка
`release-rollout.yml` (тег и доля): новая доля в `update.json`, новая подпись и их строки в `SHA256SUMS`. Служба берет
выпуск, только если номер этой установки из 0–99 меньше доли (раздел «Проверка обновлений»). Доля 0 — стоп-кран: выпуск
больше никому не предлагается, служба пишет «раскатка остановлена» и берет предыдущий (инцидент —
[docs/operations/support.md](../operations/support.md)). Порядок выпуска по шагам — [docs/operations/checklist.md](../operations/checklist.md).

`scripts/tests/release-assembly-smoke.sh` (задание «Стиль и формат») проверяет сборщик на собранных здесь сборках: суммы,
канал и доля, файлы ОС в манифесте, заметки вне файлов выпуска, бета, порча, сборка без ОС, неверная доля, `rollout`; и
подпись на ключе, созданном там же: `openssl` проверяет ее открытым ключом, измененный манифест ее не проходит, `rollout`
подписывает заново, ключ не из папки ключей, ключи без секрета и `rollout` подписанного без ключа — ошибка.

## Подпись обновлений

Обновление ставит служба — от SYSTEM или root, поэтому выпуск проверяется не только HTTPS GitHub, но и своей подписью:
манифест `update.json` подписан ключом ECDSA P-256 (SHA-256, подпись DER в base64 — `update.json.sig`), а суммы файлов ОС
в нем — SHA-256 того, что служба скачает. Подменить файл, не подделав подпись, нельзя ни на GitHub, ни по дороге.

- **Открытые ключи** — `shared/update/keys/*.pem`, служба встраивает их в себя (`UpdateChecker.EmbeddedKeys`). Подходит
  любой: новый ключ добавляется рядом, старый уходит через выпуск, когда все обновились.
- **Закрытый ключ** — только в секрете GitHub `UPDATE_SIGNING_KEY` (PEM PKCS#8) и у владельца в менеджере паролей. Не в
  Git, не в чате, не в журналах.
- `release.cs assemble` подписывает манифест ключом из секрета и сразу сверяет подпись с открытыми ключами репозитория:
  не сходится (секрет и ключ в репозитории разошлись) — ошибка, выпуска нет. Секрета нет: пока ключей в репозитории нет —
  выпуск без подписи (служба его не поставит, окно говорит «с первого подписанного выпуска»), а если ключи уже есть —
  ошибка. `rollout` подписывает заново; подписанный манифест без ключа не меняется.

Новый ключ (один раз, на своем компьютере):

1. `dotnet run scripts/release.cs keygen ~/private-gateway-update-key.pem` — закрытый ключ в файл вне репозитория
   (права 600; внутри репозитория и поверх старого — отказ), открытый — в `shared/update/keys/<год-месяц>.pem`.
2. GitHub → репозиторий → **Settings** → **Secrets and variables** → **Actions** → **New repository secret**: **Name** —
   `UPDATE_SIGNING_KEY`, **Secret** — все содержимое файла закрытого ключа → **Add secret**.
3. Закрытый ключ — в менеджер паролей, файл удалить.
4. Открытый ключ закоммитить: служба следующей версии примет выпуски, подписанные этим ключом.

## Проверка обновлений

Ищет обновление служба (в окне сеть запрещена) — `UpdateChecker`, IPC `CheckForUpdate(канал, force)`:

1. Список выпусков — API GitHub (`/repos/rvburov/private-gateway-client/releases?per_page=20`, без учетной записи:
   репозиторий открытый), черновики и теги не `v<SemVer>` — мимо. Канал «Стабильный» не видит предварительных выпусков.
2. От новых к старым, пока версия выше установленной: у выпуска есть `update.json` и `update.json.sig` — загрузки
   выпусков этого репозитория (другие ссылки не берутся), подпись сходится с ключом программы, версия в манифесте — та
   же, что в теге, бета-манифест не в стабильном канале, номер установки меньше доли раскатки. Не подошел — причина в
   журнал службы, дальше следующий: пока новейший раскатывается, установка получает предыдущий.
3. Ответ — «нет подписанных выпусков» (в службе нет ключей; в сеть служба тогда не ходит), «последняя версия»,
   «доступна X» (главное из заметок, страница выпуска) или «не удалось» (нет сети, отказ GitHub, файл больше предела —
   манифест не больше 64 КБ, список — 4 МБ). Ответ служба помнит час на канал; неудачу — нет.

Номер установки для раскатки — случайный 0–99, один раз (`update-bucket` в папке состояния службы): по нему установку не
отличить от сотой части других. Версия, с которой пользователь откатился (`left-version`), не предлагается — только
более новая. Окно спрашивает службу через две минуты после запуска и раз в 12 часов, если включено
«Проверять сами» (по умолчанию), при смене канала и при открытии «О программе»; выключено — только кнопкой «Проверить»
(`UpdateWatcher`, docs/architecture/ui.md).

## Установка обновления

Ставит обновление служба — та установленная, что программа поставлена установщиком (`UpdateInstaller.ForThisMachine`):
Windows — MSI (ключ реестра его ярлыка), Linux — пакет `.deb` (его знает dpkg) или `.rpm` (его знает rpm). Архив, служба
пользователя и macOS — нет: окно ведет на страницу выпуска («Открыть выпуск»).

1. «Обновить сейчас» — IPC `DownloadUpdate(версия)`: только версию, которую служба сама нашла последней проверкой. Файл
   своей ОС из подписанного манифеста — по адресу загрузок этого репозитория — в `updates` папки состояния службы (пишет
   туда только служба), с ходом загрузки окну; размер не больше и SHA-256 — как в манифесте, иначе файл удаляется и
   окно получает отказ. Уже скачанное и сверенное заново не качается, прежние загрузки убираются.
2. «Перезапустить клиент» — `InstallUpdate(версия)`: служба сверяет файл еще раз и запускает установщик ОС отдельно от
   себя, ответ — номер его процесса. Windows: `msiexec /i … /qn OWNER=<владелец службы>` от SYSTEM (без запроса UAC: служба
   ставит только подписанное). Linux: `systemd-run --scope` — `apt-get install --allow-downgrades` (нет apt — `dpkg -i`)
   или `rpm -U`: установщик живет в своей области systemd и переживает перезапуск службы. Вывод — в `updates/install.log`.
3. Окно назначает себе запуск после установщика (`AppRelauncher`: на Windows — файл команд во временной папке
   пользователя ждет процесс через `tasklist`, на Linux — `sh` ждет `/proc/<номер>`) и закрывается, освобождая свои файлы.
   Установщик заменяет программу и ставит службу атомарно (ServiceSetup): не встала новая — работает прежняя, а MSI
   откатывается целиком. Потом открывается окно новой версии.

На время замены службы блок при обрыве (если включен) держит трафик: он переживает остановку службы, а новая служба
подключается к последнему серверу сама. Без блока при обрыве на это время защиты нет — карточка «Обновление готово»
говорит это прямо.

### Откат на прежнюю версию

Служба при каждом запуске записывает свою версию (`version` в папке состояния); стояла другая — запоминает ее
(`VersionHistory`): старше — как прежнюю (`previous-version`, на нее можно вернуться), новее — как ту, с которой
откатились (`left-version`, ее больше не предлагать). Проверка обновлений тем же списком выпусков смотрит:

- прежняя версия — ее выпуск на GitHub подписан ключом программы, версия в манифесте та же, в нем есть файл этой
  установки: ответ `UpdateOffer.rollback`, в «О программе» — «Прежняя версия 0.1.0» и «Откатить на 0.1.0»; почему нельзя
  — в журнал службы;
- нынешняя версия, когда есть обновление, — так же: тогда на карточке «Подпись проверена · можно откатить на 0.1.0»
  (`return_to`, доска 15); нет подписанного выпуска нынешней — не обещается.

Откат идет теми же `DownloadUpdate` и `InstallUpdate` с номером прежней версии (служба принимает только найденное ею
обновление или найденную ею прежнюю версию) и тем же установщиком ОС: MSI с разрешенным понижением версии,
`apt-get install --allow-downgrades`, `dpkg -i`, `rpm -U --oldpackage`. Пакеты Linux понижают версию как обновление:
служба переставляется для того же владельца. Канал и раскатка для отката не важны — эту версию ставили на этой машине.
Откатиться можно на одну версию назад, а после отката — только обновиться на более новую, чем та, с которой ушли.

## Лицензии открытых компонентов

Список компонентов один — `shared/licenses/components.json`: из него экран «О программе» показывает «Лицензии открытых
компонентов» (Client.UI встраивает файл), а `scripts/package.cs` пишет `THIRD-PARTY-NOTICES.txt` в выпуск. У каждого
компонента — имя, выражение SPDX, строка авторства, ссылка и чем он приходит: пакеты NuGet (`*` в конце — любой хвост
имени), свои файлы (шрифты окна), ядро из `shared/cores` (со ссылкой на исходники этой версии — для GPL sing-box) или
геобаза.

`THIRD-PARTY-NOTICES.txt`:

- компоненты выпуска с версиями, авторством, ссылками, пакетами и обязательными строками авторства данных;
- полные тексты лицензий из `shared/licenses/texts/<SPDX>.txt` (канонические тексты SPDX), каждый один раз;
- уведомления, которые пакеты NuGet приносят сами (`THIRD-PARTY-NOTICES` .NET, SkiaSharp и HarfBuzz с их встроенными
  библиотеками, CommunityToolkit), одинаковые — один раз со списком пакетов.

Что держит список полным:

- сборка выпуска — каждый пакет из SBOM (вместе с пришедшими через другие пакеты) покрыт строкой списка, у каждой
  лицензии есть текст; иначе ошибка;
- тесты `AboutPageTests` — каждый пакет проектов и каждый шрифт окна в списке, у каждого компонента есть авторство и
  ссылка, у каждой лицензии — текст, лишних текстов нет, каждое ядро из `shared/cores` в списке;
- `release-smoke.sh` — в архиве есть уведомления с текстами GPL и MPL, ссылкой на исходники sing-box, JetBrains Mono и
  геобазой сайтов со ссылкой на ее коммит domain-list-community; Xray из архива читает `geosite:category-ads-all`
  (`xray run -test`).

## Проверка

`scripts/tests/release-smoke.sh <версия>` (шаг `publish.yml` на каждой ОС): суммы сходятся; архив распаковывается; в
нем окно, служба, ядра, геобазы и SBOM, у исполняемых файлов есть право на запуск; служба из архива запускается без
`DOTNET_ROOT` и `dotnet` в `PATH` и называет версию выпуска; ядра запускаются; SBOM в архиве тот же, что рядом с ним, и
называет оба ядра. Готовый выпуск — артефакт `release-<ОС>` запуска workflow.

`publish.yml` идет на тег `v*` (версия — из тега), по кнопке (версия — поле ввода) и на ветках, когда меняется сама
сборка (скрипты выпуска и ядер, `shared/cores`, проекты и версии пакетов).
