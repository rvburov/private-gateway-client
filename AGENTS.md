# AGENTS.md

Указания для ИИ-агентов (Claude Code, Codex, Copilot, Cursor и других), которые работают в этом
репозитории. Здесь то, что нужно знать до первой правки. План работ — [README.md](README.md)
(ROADMAP), принятые решения — [docs/roadmap/DECISIONS.md](docs/roadmap/DECISIONS.md), макет —
[docs/design](docs/design/README.md).

Правила перенесены из SmartBase и адаптированы (источник — [docs/sources/REUSE_REGISTER.md](docs/sources/REUSE_REGISTER.md)).

## Параллельная работа агентов — прежде всего

Пользователь работает с разных ОС (Windows, macOS, Linux) и ведет одновременно несколько чатов
Claude Code и других ИИ. Мест работы два вида:

| Где | Агенты | Рабочее место |
| --- | --- | --- |
| **Компьютер с основной папкой репозитория** | Claude Code, Codex CLI, Cursor, Copilot и другие ИИ | своя рабочая папка (git worktree) и ветка — пункты 1–7 |
| **Облачная копия** | Claude Code в облаке, Codex Cloud и другие облачные агенты | вся копия своя, рабочие папки не нужны — «Облачная копия» ниже |

**Основная ветка — `master`** (ветка по умолчанию на GitHub). Ниже она так и называется.

**Команды везде одни — bash.** Скрипты проекта запускаются как `scripts/…` на любой ОС: на
Windows — в Git Bash, на macOS и Linux — в терминале, в облаке — в его shell. Команды PowerShell
и cmd в скрипты и инструкции разработчику не писать, пути — через `/`. Исключение — инструкция
пользователю для того, что в Git Bash не делается: установка службы, брандмауэр, установка .NET.

Ни одна работа не должна потеряться и ни один агент не должен испортить работу другого, поэтому:

1. **В основной папке репозитория агенты не работают.** Каждый чат любой программы — в своей
   рабочей папке (git worktree) на своей ветке, даже если сейчас он один. В основной папке
   только `master`: сюда вливается готовая работа, отсюда пользователь запускает программу.
2. **В начале чата** — `scripts/worktree.sh check` (на Windows из Git Bash) и показать
   пользователю все, что помечено: незакоммиченное, не влитое в `master`, не отправленное на
   GitHub, `master` на GitHub впереди локального, папки не на месте, **чужие ветки на GitHub,
   которые меняют те же файлы** («ПЕРЕСЕЧЕНИЕ»). Пересечение — сказать пользователю в начале
   задачи. Чужие папки и ветки не трогать.
3. **Своя папка** — внутри основной, в каталоге с точкой:
   - **Claude Code** — `EnterWorktree` с именем: папка `.claude/worktrees/<имя>`, ветка
     `worktree-<имя>`;
   - **остальные ИИ** — `scripts/worktree.sh new <имя>`: папка `.agents/worktrees/<имя>`, ветка
     `<имя>` от локального `master`.

   Дальше работать только в ней. Имя — по сути задачи (`kill-switch`, `fix-import`): латиница,
   цифры, дефис, до 20 знаков — длиннее на Windows не даст лимит пути в 260 знаков.
4. **«Сделай коммит» в рабочей папке — это коммит и сразу перенос в `master`:** коммит в свою
   ветку от имени пользователя и без подписи (раздел «Git») → `scripts/worktree.sh sync` →
   тесты → `scripts/worktree.sh merge`. Если `merge` отказал, потому что `master` ушел вперед, —
   снова `sync`, тесты, `merge`. Сообщать «сделано» — только после строки «В master влито».

   **«Сделай и отправь» — всегда, без просьбы** (правило пользователя «делать все
   самостоятельно», раздел «Работа с пользователем»). Закончив работу: тесты → коммит → `sync` →
   тесты → `merge` → проверка автора → gitleaks → `git push origin master` из основной папки, только
   перемоткой. Остановиться и сказать пользователю, ничего не отправляя, если: тесты упали или
   пропущены не из-за известной среды; конфликт при `sync`, где обе стороны меняли одну логику;
   нужна принудительная перезапись истории; push отклонили три раза подряд.

   **Задача «сделай через PR»** — тесты → коммит в свою ветку → push ветки → PR в `master`
   (заголовок и описание по-русски: что, зачем, как проверено; без подписей ИИ) → дождаться
   зеленой проверки → дать ссылку. Сливает пользователь — если сам попросил PR.
5. **Перед последним ответом в чате** — снова `scripts/worktree.sh check` и назвать все помеченное.
6. **Папку и ветку убирать только по слову пользователя** — `scripts/worktree.sh remove <имя>`
   (у Claude Code еще `ExitWorktree` с `remove`): оба откажут, если есть незакоммиченное или не
   влитое. `discard_changes`, `git worktree remove --force`, `git branch -D`, `git reset --hard`,
   `git clean` и удаление папок руками — запрещены.
7. **В других местах проекта рабочих папок не создавать.** `check` помечает такие папки —
   показать пользователю.

**Claude Code:** из рабочей папки он не пускает git в основную, поэтому `merge` так:
`ExitWorktree` с `keep` → в основной папке `scripts/worktree.sh merge <имя>` → снова
`EnterWorktree` с `path`, если работа продолжается.

### Общее на одной машине — по одному агенту за раз

VPN-клиент меняет состояние всей машины, поэтому одновременно может работать только один агент:

- **служба Private Gateway, TUN-адаптер, правила брандмауэра** (WFP на Windows, nftables на
  Linux), маршруты и DNS. Тесты групп Network и Security, которые их трогают, — только когда
  другие агенты не гоняют такие же. Перед запуском проверить, не запущена ли уже служба или
  тестовый процесс;
- **порты** локальных входов ядра (SOCKS/HTTP) и канал IPC службы;
- **блок при обрыве**: включенный агентом блок отрезает интернет всем на машине, включая других
  агентов. После теста — убедиться, что правила сняты;
- **кеш пакетов** общий: рабочая папка берет его из основной (`Directory.Build.props`). Не чистить
  и не ставить на него ссылок внутри рабочей папки.

На компьютере пользователя без его согласия не устанавливать службу, не включать блок при обрыве
и не менять брандмауэр, маршруты и DNS.

### Облачная копия

Облачная сессия получает свежий клон с GitHub в отдельной машине, которая исчезает, когда среда
истекает. Правила другие:

- **Рабочих папок не заводить** — работать в самой копии, на ветке, которую дала среда.
  `scripts/worktree.sh check` в облаке (`CLAUDE_CODE_REMOTE=true`) показывает незакоммиченное,
  не отправленное на GitHub и не влитое в `master` на GitHub.
- **Автор коммитов.** У Claude Code в облаке хук `SessionStart` (`.claude/settings.json`)
  запускает `scripts/cloud-session.sh`: автор и коммитер — пользователь, подпись выключена; там
  же отключены подписи Claude в коммитах и PR. Другие облачные агенты выполняют команды из
  раздела «Git» сами.
- **Неотправленная работа живет только в машине сессии.** Коммит в ветку копии отправлять на
  GitHub сразу (`git push -u origin HEAD`): своя ветка ни во что не вливается.
- **В `master` агент вливает сам, без просьбы** (правило пользователя «делать все
  самостоятельно»), когда работа готова: тесты → коммит → push ветки → проверка CI на ветке
  зеленая на трех ОС → `git fetch origin` → `git rebase origin/master` → тесты → проверка автора →
  gitleaks → `git push origin HEAD:master` обычной перемоткой. Отклонили — никакой принудительной
  отправки: `fetch` → `rebase` → тесты заново → push; три отказа подряд — остановиться и сказать
  пользователю. Открытый PR после такой отправки GitHub закрывает сам как слитый.
- **Чего в облаке нет:**
  - экрана — интерфейс проверять только тестами без экрана (Avalonia.Headless);
  - прав и устройств для TUN, брандмауэра и службы — тесты, которым они нужны, уходят в Skipped,
    так и писать в отчете;
  - бывает, что нет .NET SDK, а загрузка с сайта Microsoft закрыта сетью среды — ставить пакетом
    ОС: `apt-get install -y dotnet-sdk-10.0`;
  - доступа к GitHub-репозиториям, кроме подключенных к сессии;
  - загрузки выпусков GitHub — ядро Xray для тестов `Network` собирать из исходников:
    `scripts/get-xray.sh --build` (нужен go, модули идут через proxy.golang.org).

## Проект

Private Gateway Client — самостоятельный прокси/VPN-клиент с ручным выбором сервера, полной
системной маршрутизацией и защитой от утечек (блок при обрыве, DNS, IPv6). Десктоп — C# · .NET 10 ·
Avalonia 12 для Windows, macOS и Linux; затем Android (Kotlin) и iOS (Swift). Ядро — Xray-core
(готовые сборки, своего кода на Go нет); TUN режима VPN — sing-box отдельным процессом (GPL-3.0), он
же вероятно для Hysteria2/TUIC.

Где что лежит:

- `PrivateGateway.slnx` — решение, все команды ниже запускаются из корня;
- `desktop/src/` — проекты десктопа, слои — в разделе «Правила кода»;
- `desktop/tests/` — тесты: `Unit` (быстрый гейт), `Architecture` (границы модулей), `UI`
  (интерфейс без экрана, снимки в `artifacts/ui-snapshots`), `Network` (настоящее ядро Xray на
  127.0.0.1: сборку кладет `scripts/get-xray.sh`, в облаке — `scripts/get-xray.sh --build`; тесту
  туннеля нужны еще sing-box — `scripts/get-singbox.sh` — и root на Linux с `ip`, `curl` и `python3`,
  тесту блока при обрыве — еще `nft`, тесту покрытия — `git`, `getent` и `setpriv`; правила и TUN ставятся только в своем сетевом пространстве;
  без сборок и прав эти тесты пропускаются), дальше
  `Integration`, `Security` — по мере появления кода;
- `shared/specifications/` — общее для всех платформ: `design-tokens.json`, тексты RU/EN
  (`localization/*.json`), контракт IPC (`ipc/*.proto`);
- `shared/testdata/` — эталонные обезличенные ссылки и подписки для тестов разбора на всех ОС;
- `shared/licenses/` — открытые компоненты программы (`components.json`: экран «О программе» и THIRD-PARTY-NOTICES
  выпуска) и полные тексты их лицензий;
- `docs/` — `design/` (макет v1.0), `architecture/`, `security/`, `roadmap/`, `sources/`;
- `scripts/` — `worktree.sh`, `cloud-session.sh` и скрипты сборки;
- `artifacts/` — вывод сборки, `packages/` — кеш NuGet, `.localdata/` — данные отладочного
  запуска; все три не в git.

## Сборка и запуск

```bash
dotnet build PrivateGateway.slnx                       # все проекты
dotnet run --project desktop/src/Client.UI             # интерфейс
dotnet run --project desktop/src/Client.UI -- --demo   # интерфейс на имитации службы, с демо-серверами
dotnet run --project desktop/src/Client.Service -- --version
dotnet run scripts/gen-tokens.cs                       # тема Avalonia из design-tokens.json
scripts/publish.sh [версия]                            # выпуск для ОС этой машины: архив, SBOM, SHA256SUMS
scripts/package-linux.sh <версия>                      # .deb и .rpm из сборки выпуска (нужен nfpm)
scripts/package-windows.sh <версия>                    # MSI из сборки выпуска (Git Bash, нужен wix 5.0.2)
git tag v1.2.3 && git push origin v1.2.3                # выпуск на GitHub (release.yml); 1.3.0-beta.1 — бета
dotnet run scripts/release.cs keygen <файл вне репозитория> # ключ подписи обновлений (делает пользователь, release.md)
dotnet run scripts/gen-icons.cs                        # значок программы (SVG, ICO) из Icons.axaml и токенов
```

- Вывод сборки — в `artifacts/bin/<проект>/debug/`, выпуска — в `artifacts/release/`
  ([docs/architecture/release.md](docs/architecture/release.md)). Версии пакетов — только в `Directory.Packages.props`.
- Предупреждения — ошибки (`TreatWarningsAsErrors`): сборка с предупреждением не проходит.
- Пользователь запускает программу из основной папки, и сборка там падает на занятых файлах. У
  рабочей папки агента своя `artifacts/`. Процесс программы и службы не завершать и закрыть не
  просить, если пользователь сам не хочет посмотреть изменения.

## Тесты

```bash
dotnet test --solution PrivateGateway.slnx            # все тесты (Microsoft.Testing.Platform)
dotnet test --project desktop/tests/Unit               # быстрый гейт
scripts/soak.sh 30                                     # долгий прогон (soak), минут на режим; VPN — Linux от root
dotnet format PrivateGateway.slnx                      # стиль и формат по .editorconfig (CI — с --verify-no-changes)
dotnet test --solution PrivateGateway.slnx --results-directory artifacts/test-results --report-ctrf
dotnet run scripts/test-report.cs artifacts/test-results   # итог и пропуски по причинам, как в CI
```

- **Тесты гонять всегда.** По ходу работы — `Unit`, перед коммитом — все. В отчете — числа
  прогона (total / failed / succeeded / skipped); упавшее или пропущенное не выдавать за прошедшее.
- **Проверенное на стенде — не то же, что проверенное у пользователя.** В отчете разделять: тесты
  на собранных в тесте данных, проверку на реальной машине с TUN и брандмауэром, проверку
  пользователем в работающей программе. Без реальной сети и прав так и писать: «проверено в тестах,
  на вашей машине не проверено» — и что именно проверить.
- **Новый тест проверять мутантами:** испортить код и убедиться, что тест падает; после возврата
  исходника — `touch` или прогон с `--no-incremental`.
- Тесты разбора ссылок и подписок — на эталонах из `shared/testdata`, одних для всех платформ.
- **Пропуск — только с причиной, и CI ее сверяет.** Тест без условий (ОС, права, сборки ядер) пропускается через
  `Assert.Skip…` с причиной словами. Отчет CI (`scripts/test-report.cs`) пишет каждый пропуск с причиной в сводку
  задания и падает на пропуске, которого нет для этой ОС в `desktop/tests/allowed-skips.json`. Законный пропуск —
  строка туда с объяснением; тест, который должен идти в CI, — вернуть ему условия (шаг workflow, права, ядро).
- **Стиль — `dotnet format`:** CI проверяет его с `--verify-no-changes`. Перед коммитом — `dotnet format
  PrivateGateway.slnx`, если правились файлы `.cs`.

## Правила кода

- **Общий стиль — без отступлений.** Код — как окружающий: имена, идиомы, плотность и язык
  комментариев (русский). `.editorconfig` и анализаторы держат стиль при сборке.
- **Слои и разрешенные ссылки** (держат тесты `Architecture`, подробно —
  [docs/architecture/overview.md](docs/architecture/overview.md)):

  | Проект | Может ссылаться на |
  | --- | --- |
  | `Client.Core` | — |
  | `Client.Contracts` | Core |
  | `Client.Network` | Core |
  | `Client.Application` | Core, Contracts, Network |
  | `Client.Infrastructure` | Core, Contracts, Application |
  | `Client.Platform.*` | Core |
  | `Client.Service` | Core, Contracts, Network, Platform.* |
  | `Client.UI` | Core, Contracts, Application, Infrastructure |

  Новый проект — сначала строка в этой таблице, в `ModuleBoundariesTests` и в обзоре архитектуры.
- **Интерфейс не управляет сетью.** В Core, Network, Application и UI запрещены HTTP, сокеты, DNS,
  пинг и запуск программ (`desktop/BannedSymbols.NoNetwork.txt`, анализатор RS0030). Новых
  `#pragma warning disable RS0030` не добавлять. Сеть процесса интерфейса — только загрузка
  списков серверов в Infrastructure; все остальное — служба.
- **Служба не принимает готовый конфиг ядра, пути и команды** — только описание сервера и
  настройки по контракту IPC. Конфиг Xray/sing-box служба собирает и проверяет сама.
- **Контракт IPC** — `shared/specifications/ipc/*.proto`. Несовместимое изменение — новая версия
  пакета (`v2`), старую служба поддерживает. Новое значение перечисления — строка в
  `ContractMapping` (иначе падают тесты).
- **Интерфейс — из токенов макета.** Цвета, шрифты, отступы, скругления — только из
  `shared/specifications/design-tokens.json` через ресурсы темы (`Tokens.axaml` генерирует
  `scripts/gen-tokens.cs`); значения вручную в разметке не задавать, шестнадцатеричные цвета в
  разметке ловит тест. Тексты — только из `shared/specifications/localization`. Новый блок — по
  правилам [docs/design/README.md](docs/design/README.md), устройство — [docs/architecture/ui.md](docs/architecture/ui.md).
- **Состояния защиты** меняются только через `ConnectionStateMachine`.

## Источники и лицензии

- Перед переносом кода из любого репозитория — запись в
  [docs/sources/REUSE_REGISTER.md](docs/sources/REUSE_REGISTER.md): задача → URL файла и коммита
  → лицензия → что переносим или пишем заново → тесты → решение. Непроверенную ссылку не выдавать
  за проверенный файл.
- **Hiddify — код не копировать** до отдельной юридической проверки (лицензия с дополнительными
  условиями). Изучать можно идеи и документированные форматы.
- **PRIVATE GATEWAY** (сервер) — источник форматов ссылок и подписок для тестов совместимости.
  Секреты, ключи, реальные адреса подписок, UUID устройств и учетные данные не переносить.
- sing-box — GPL-3.0: запускать отдельным процессом, в код не встраивать.
- **Новый пакет, шрифт или ядро — строка в `shared/licenses/components.json`** (авторство, ссылка, SPDX) и текст
  лицензии в `shared/licenses/texts`, если ее там еще нет. Без строки падают тесты «О программе» и сборка выпуска.

## Тексты: интерфейс, документация, комментарии

- **Буквы «е с точками» нет нигде в текстах** — ни в подписях интерфейса, ни в документации, ни в
  комментариях. Пишется «е». (Исходники макета `docs/design/mockup` заморожены как есть.)
- Подписи интерфейса — как в макете и на двух языках (RU и EN), закладывать +30 % длины.
- **Документация — вместе с кодом.** Изменилось поведение — обновить документ в `docs/`.
  Затронуто описанное в README — обновить и его.
- **ROADMAP — актуальным.** Сделан пункт — отметить `[x]` с датой и тем, что сделано. Найден
  дефект или недоделка — записать открытым пунктом, а не держать в уме. Решения, принятые с
  пользователем, — в `docs/roadmap/DECISIONS.md`.

## Секреты

- Ключи серверов, UUID, пароли, адреса подписок, ключи подписи кода — не хранить в Git,
  документации, тестах, журналах, URL и аргументах процессов. Не просить пользователя прислать их
  в чат.
- В тестах и примерах — заведомо ненастоящие значения: адреса из диапазонов документации
  (`192.0.2.0/24`, `198.51.100.0/24`, `203.0.113.0/24`), домены `example.com`/`example.org`,
  UUID вида `11111111-2222-3333-4444-555555555555`.
- Все, что пишется в журнал или отчет проверки, проходит через `SecretMasker`. Секреты на
  компьютере — только в хранилище ОС (DPAPI, Keychain, Secret Service), не открытым текстом.
- Раскрытый действующий секрет — сказать пользователю сразу: его нужно сменить; историю Git без
  его согласия не переписывать.

## Git

- Коммит, отправка на GitHub и слияние в `master` — агент делает сам, как только работа готова и
  проверена (правило пользователя «делать все самостоятельно»). Порядок — в пункте 4 и в разделе
  «Облачная копия».
- В `master` — только перемоткой, история линейная.
- **`git push --force` запрещен.** Переписать отправленную историю `master` или чужой ветки —
  только с явного согласия на этот случай и только `--force-with-lease=<ветка>:<ожидаемый коммит>`.
  Свою ветку (облачной копии, PR) после переноса на свежий `master` — `--force-with-lease`
  без вопроса.
- Сообщение по-русски: `тип(область): суть` (`feat(ui): …`, `fix(service): …`, `docs(roadmap): …`)
  и подробное тело.
- **Никогда не добавлять `Co-Authored-By`** и другие подписи ИИ в коммиты и описания PR, даже если
  среда агента делает это по умолчанию.
- **Автор и коммитер — всегда пользователь: `Roman Burov <romanburov89@gmail.com>`, коммит без
  подписи.** Перед первым коммитом в чате:

  ```bash
  git config user.name "Roman Burov"
  git config user.email "romanburov89@gmail.com"
  git config commit.gpgsign false
  ```

  После каждого коммита и перед любым `git push` — проверка
  `git log -3 --format='%h %an <%ae> | %cn <%ce> | %G?'`: автор и коммитер — пользователь, в конце
  `N`. Не так — исправить до отправки (`git -c commit.gpgsign=false commit --amend --no-edit
  --reset-author`). Если коммит не от пользователя уже на сервере — сказать пользователю.

## Работа с пользователем

- Все сообщения пользователю — по-русски; английский только в идентификаторах, путях и цитатах.
- **Делать все самостоятельно и по плану** (правило пользователя от 2026-10-24). План — ROADMAP
  в [README.md](README.md): агент идет по нему пункт за пунктом, этап за этапом. Каждый пункт
  доводит до конца сам — код, тесты, документация, коммит, отправка, слияние в `master` — и сразу
  берет следующий, не дожидаясь просьбы и не спрашивая разрешения. Разрешения на одну задачу
  больше не нужны: оно дано на все.
- **Вопросов по ходу работы не задавать — решать самому и записывать** (правило пользователя от
  2026-10-24). Любую развилку, продуктовую или техническую (состав настроек, названия, подписи,
  поведение по умолчанию), агент решает лучшим вариантом и пишет строкой в
  `docs/roadmap/AGENT-DECISIONS.md`: номер, дата, решение, варианты, почему. Пользователь
  рассматривает и обсуждает записанное после того, как код готов; что он поменяет — переделать.
  В отчете назвать номера новых решений, которые стоит посмотреть.
- Исключения — только то, что агент сделать не может или не вправе без согласия: запрет среды на
  действие, правка вне репозитория, перезапись отправленной истории, а на компьютере
  пользователя — служба, блок при обрыве, брандмауэр, маршруты и DNS (раздел «Общее на одной
  машине»). Тогда — остановиться на этом шаге, остальное доделать и сказать, что нужно от
  пользователя.
- Принятые решения — в `docs/roadmap/DECISIONS.md` и ROADMAP; не переигрывать их без пользователя.
- **Не повторять другие программы, а делать лучше.** «Так устроено у всех» — не довод.
- Инструкция пользователю — один путь по шагам с точными названиями полей окна.
- Работать самому, без многоагентных разборов и подагентов, пока пользователь прямо не попросит.
